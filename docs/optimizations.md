## Решения

### Онлайн-детект на сокете; health выпилен

- `isOnline` пишется из событий Echo-соединения: `connected`
  → онлайн мгновенно; `disconnected`/`unavailable`/`failed`
  → офлайн с грейс-периодом 2–3 с (краткий флап WiFi не дёргает
  плеер). HTTP-зонд в детекте не участвует.
- Уточнение 2026-11-27 (вечер): грейс распространён и на
  `unavailable`/`failed` (pusher шлёт их между ретраями —
  мгновенный офлайн мигал баннером); в createEcho заданы
  `activity_timeout` 15 с / `pong_timeout` 5 с — убитый
  контейнер реверба за DNAT докера не шлёт FIN, дефолтные
  ~2 мин pusher'а проигрывали серверному грейсу стопа (60 с);
  баннер «Офлайн-режим» перенесён в App.vue (был только на
  главной — вне её офлайн был не виден вовсе).
- `GET /health`, поллер, `probeHealth`, журнал зондов —
  удаляются целиком. Кнопки «переподключиться» юзеру не
  показываем: это служебное движение, не действие пользователя.
- Уточнение 2026-11-28 (баг 14): вернулся один разовый
  стартовый зонд (`probeAtStartup` в сторе онлайна) — fetch
  no-cors на выбранный endpoint, таймаут 2,5 с, плюс мгновенный
  офлайн при `navigator.onLine === false`. Без него мёртвый бэк
  при запуске обнаруживался только таймаутами сокета (~15 с
  «думания»). Это не поллер: один запрос на запуск приложения,
  онлайн по-прежнему подтверждает только сокет.
- Ложный «онлайн» (сокет жив, HTTP бэка умер) ловим серией
  сетевых/5xx фейлов запросов → перевод флага в офлайн.
  Ручной «проверить HTTP» не предусмотрен — костылей
  накопления не делаем.
- Смена пары адресов (`resolveEndpoint`, кулдаун 60 с)
  инициируется падением сокета, а не промахом зонда.
- Уточнение 2026-11-27 (вечер): гвард роутера запускал
  `bootstrap()` сам, мимо цепочки main.ts — монтирование
  стартовой страницы обгоняло ipify, и первые запросы
  (карточки Яндекса/YouTube на «Настройках») улетали на
  дефолтный WAN (`blocked:mixed-content` у https-страницы,
  свайп-обновление потом шло уже верно). Стартовый выбор пары
  мемоизирован в `endpointReady()` (lib/endpoints), гвард и
  main.ts ждут один promise; повторные вызовы `resolveEndpoint`
  (переспрос по сокету, кулдаун 60 с) не трогаем.
- Бутстрэп ждёт `connected` сокета (до логина приватный
  канал не нужен — Reverb принимает анонимное соединение)
  или таймаут старта.
- Диагностика сети: журнал сокетных событий (таймстампы
  connect/disconnect, close-коды, ретраи) вместо журнала
  зондов. Экран «Настройки → Диагностика сети» перерабатывается.

### Офлайн-гейт запросов

- В офлайне axios-интерцептор режет все запросы (здоровье
  бэка здесь больше не проверяем — whitelist не нужен).
- Ошибки kind `offline` молчат: никаких тостов «Нет
  соединения» и дедлоков в очереди axios. Чтение из локальных
  сторов (кеш избранного, скачанное) продолжает работать.

### Сортировка — перенос одного элемента, не весь список

- Сейчас каждая перестановка шлёт полный массив: вкладка
  избранного целиком (`PATCH favorites/sort`), все id
  ожидающих очереди (`PATCH player/queue/reorder`), очередь
  друга (`PATCH friends/{id}/queue/reorder`), порядок треков
  плейлиста (`PATCH playlists/{id}/items/reorder`).
- Контракт меняется на «один перенос»: идентичность элемента
  + целевая позиция (или якорь — элемент, перед которым
  встать; точнее при правках с другого устройства). Бэк
  сдвигает только затронутый диапазон, всю таблицу не
  переписывает.
- Пакет для бэк-агента (4 эндпоинта), фронт подгоняется
  после контракта.

### Кеш поиска на бэке

- Ключ `(user, q, page, фильтры)`, TTL 5–15 мин, per-user.
- Одним выстрелом: второе устройство не бьёт YouTube повторно,
  пагинация контекста (`context-resolver` гоняет до 10
  страниц поиска за резолв) уходит в кеш, повторные поиски
  бесплатны. Дедуп одновременных запросов одного юзера.
- Бэк-онли, фронт не меняется.

### Реформа страницы поиска

- Две табы сверху: «Аудио» / «Видео». У каждой — свои
  пилюли секций; у «Видео» дополнительно фильтр источника
  (Дзен первым — психологически разгружаем YouTube, YouTube
  последним). У «Аудио» видео-пилюли нет.
- Секции видео — YouTube-way: ролики, каналы, плейлисты.
- Видео отображаем плитками (2 колонки, превью 16:9,
  название 2 строки) — в списке полные названия на телефоне
  не читаются.
- Дефолт активной табы — последний выбор юзера (хранится
  локально), не глобально «аудио».
- Контракт: поиск v2 — ОТДЕЛЬНЫМ эндпоинтом (текущий
  `/search` не ломаем), принимает фильтры (семейство/
  секции/источник/`type` audio|video), пагинация честно
  по-секционная. Фронт готовит форму контракта; интеграция —
  после нового дизайна страницы. Пакет бэк-агенту — ниже.
- Контекст плеера от поиска остаётся когерентным: резолв
  берёт секцию по типу текущего снапшота (как сейчас).

### Клипы только на активном устройстве

- ✅ Сделано 2026-11-27 (фронт): потоки/get-url/транспорт видео —
  только на `isActiveDevice`; пульт резолвит клип ради названия и
  обложки, поток не тянет; активация подхватывает поток с общей
  позиции.
- Было: клип резолвит и тянет потоки КАЖДОЕ устройство (пульт в
  mute): N устройств = N видео-потоков в разном качестве + N вызовов
  get-url.

### Ручная привязка видео к треку

- Меню видео → «Привязать к треку»: пикер избранных треков,
  хранится на бэке. `/videos/resolve` сначала смотрит ручную
  привязку, потом авто-матчинг.
- Лечит корень жалобы «в плеере трек, а поёт видео»: ручной
  оверрайд убирает промахи авто-матчинга.
- Контракт + фронт. Пакет бэк-агенту.

### Идентичность клипа в плеере (решение)

- При активном клипе now-playing показывает ПОЛНЫЙ
  видео-снапшот (название, обложка/кадр, меню) + строка
  «Трек: артисты — название» (источник клипа).
- Двусмысленные действия — лайк/дизлайк, в очередь, в
  очередь другу, поделиться — при активном клипе открывают
  шторку выбора «Действие с: [трек] / [видео]». В плеере и
  в контекстных меню, где эти кнопки есть. Резолв-режим
  становится полноценным: действие явно адресовано одному
  из двух снапшотов.
- Шаринг ссылкой ресурса реализован для Яндекса → у видео
  пункт «поделиться» пока disabled.
- Пульты резолвят клип ради названия, поток не тянут
  (стык с «клипы только на активном»).

### Офлайн-скачивание видео

- Снято: гигабайты HLS-сегментов, долго, прямой расход
  YouTube-прокси. Не делаем.

### Адаптивы (мелко на магнитоле/телефоне)

- Последний этап. Направление: rem-шкала + настройка кегля,
  не точечное раздувание экранов (в ките много фиксированных
  px).

### Стоп при потере активного устройства

- Активное устройство пропало (presence/socket нет дольше
  грейса 30–60 с) → бэк сам ставит серверный стейт в stop
  (позиция сохраняется). Никакого авто-выбора «кто следующий
  активный» и авто-возобновления: воспроизведение начинается
  только по явной команде юзера — play с любого устройства
  сам делает его активным (`ensureActiveForPlayback`, уже на
  фронте).
- Поведение фронта не меняется: все устройства увидят стоп
  обычным путём (стейт/сокет). Грейс нужен против Doze/флапа
  сокета: телефон в фоне держит сокет через ConnectionService
  и играет — стопа не будет; убил процесс — стоп честный.
- Бэк-пакет.

### Скачивание — без сетевых ограничений

- Wi-Fi-only не вводим: скачивание по желанию юзера в любой
  сети (решение 2026-11-27: на магнитоле Wi-Fi может и не
  быть — куда подъезжать). Текущее поведение остаётся.

### Версии и каналы обновлений

- Пока один пользователь-тестировщик: каналы Capgo не
  разводим. Стабильность железной версии → сброс версий на
  1.0.0, каналы (stable/beta) обсудим тогда.

### Лайки/дизлайки в офлайне (решение)

**Всё в этом разделе — только про ОФФЛАЙН.** В онлайне
ничего не меняется.

- Никаких новых пунктов меню и никакого фидбека волны:
  работаем только существующими «сердечко» и «убрать из
  избранного». Волна не трогается.
- Офлайн-«убрать из избранного» = локальное удаление +
  запись в буфер: {идентичность снапшота, позиция в списке
  «Моё»}.
- Офлайн-лайк — только отмена: трек из буфера → запись
  удаляется, трек возвращается на сохранённую позицию.
  Новых лайков офлайн нет (сердечко на неизбранном
  неактивно).
- Коннект: флаш буфера = `DELETE favorites` по каждой
  записи, дальше обычный ресинк. Позиция в буфере — индекс
  на момент удаления (офлайн список меняется только
  локальными действиями, индекса хватает).
- Конфликтов нет по построению: буфер живёт на одном
  устройстве, удаления монотонны, отмена возможна только до
  флаша.

### Контекстное меню строки в офлайне (решение)

- Только существующие пункты, без новых атомов. Активны:
  сердечко (отмена буферного удаления), «убрать из
  избранного», «удалить с устройства» (где есть файл).
  Остальное disabled: плейлисты, шары, деталки, скачать.
- Уточнение 2026-11-28 (баг 24): «В очередь» офлайн активно
  для скачанного — добавка кладётся локальным pending-элементом
  (офлайн-проигрывание очереди уже умел offlineNext), на
  коннекте дошивается на сервер (`syncQueueAfterConnect`);
  сыгранные/убранные офлайн добавки из буфера выпадают.

Текст для передачи бэку (шесть задач, одна отложена):

**1. Сортировка — перенос одного элемента, не весь список.**
Сейчас четыре эндпоинта принимают список целиком:
`PATCH favorites/sort` (вся вкладка с весами sort),
`PATCH player/queue/reorder` (все id ожидающих),
`PATCH friends/{user}/queue/reorder`,
`PATCH playlists/{id}/items/reorder` (`order: [index...]`).
Нужна форма «один перенос»: `{item: <конверт снапшота/id>, to_index: n}`
(либо якорь `{before: item}` — если надёжнее при правках с
другого устройства; выбери сам). Бэк сдвигает только
затронутый диапазон, всю таблицу не переписывает. Старые
формы можно выпилить сразу (фронт подгоним) или держать
параллельно один релиз — как удобнее.

**2. Кеш поиска per-user.** Кешировать `GET /search` по
ключу (user, q, page, фильтры), TTL 5–15 мин (предлагаю 10).
Боль, которую лечим: играем из поиска → второе устройство
гоняет тот же поиск заново; контекст плеера догружает до 10
страниц, каждая бьёт источники по-новой. С кешом второе
устройство и пагинация бесплатны. Заодно дедуп одновременных
одинаковых запросов юзера.

**3. Поиск v2 — ОТДЕЛЬНЫМ эндпоинтом**, текущий `/search`
не трогаем и ФРОНТ ПОИСКА НЕ МЕНЯЕМ вообще, пока бэк не
покажет, что умеют отдавать YouTube/Дзен (каналы, плейлисты
из роликов) — тогда и разберёмся с формой. Фильтры —
ТОЛЬКО строгие, без `all`: `resource` (yandex_music|upload|
skyfi|dzen|youtube — VK вычеркнут: бизнес-верификация VK ID),
`type` (audio|video — шлём всегда), секции по семейству.

**4. Привязка видео к треку — ДЕЛАТЬ СЕЙЧАС НА БЭКЕ.**
Эндпоинт ручной привязки (`/videos/resolve` сначала смотрит
ручную привязку, потом авто-матчинг). ФРОНТ НЕ ДЕЛАЕТ до
принятия дизайна (пикер из избранных треков из меню видео).

**5. Presence устройств на сокетах.**
Сейчас устройство шлёт heartbeat POST раз в 30 с, без него
бэк считает устройство офлайн; подключение второго
устройства другие устройства видят только после перелогина.
Хотим: presence держать на Reverb-соединении — коннект =
онлайн, разрыв = офлайн (грейс 30–60 с против флапа WiFi).
Нужно от бэка: связать сокет с устройством (device_uuid в
auth-handshake приватного канала или одноразовая привязка
после connect — выбери сам) и грейс перед статусом
«устройство офлайн». Heartbeat с фронта потом выключим.

**6. Стоп при потере активного устройства.**
Активное устройство (`active_device_id` плеера) пропало из
presence дольше грейса 30–60 с → сервер сам ставит стейт
плеера в stop (позиция сохраняется). Никакого авто-выбора
нового активного и авто-возобновления: play с любого
устройства сам делает его активным (это уже на фронте).

Вопросы к бэку:
- Поиск v2: каналы (YouTube-каналы) и плейлисты из роликов —
  что умеют отдавать YouTube/Дзен, и в какой форме? От этого
  зависит форма ответа v2 (ждём ответа, фронт поиск пока не
  трогаем).
- Поиск v2: has_more по видео-источникам — merge (как
  сейчас: Дзен+YouTube OR) или per-source?
- Кеш: TTL 10 мин ок? Нужна ли инвалидация (например после
  лайка внутри результатов)?
- Сортировка: to_index или before-якорь?
- Presence: ок ли device_uuid в auth-handshake?
- Стоп: грейс 60 с ок?

Фронт-заметки (не бэк): «скачать всё» на плейлисте с
видео — видео игнорируются, не скачиваются никогда

## Открытые вопросы

### Волна

Работает ок, не трогаем. Офлайн = волна играет свой список
в главном плеере, отдельного режима волны офлайн нет.
Проверено по коду: кнопка «В волну» на главной в офлайне
СЕЙЧАС ВИДНА (`Home.ts:28`, гейта на офлайн нет) — прятать
в офлайн-пакете.

### Keep-alive всех страниц (TabsLayout) — ОТЛОЖЕНО

Текущее поведение нравится: страницы живые, поиск после
возврата не перезапрашивается. НЕ трогаем. Требует
доработки позже: под keep-alive ВСЕ страницы читают живой
глобальный роут (стоит пластырь-гвард в `useEntityDetails`).
Варианты на будущее: А) keep-alive только корней вкладок,
деталки пересоздаются; Б) страницы работают со снимком
параметров роута.

Реализовано: коллекции в локальной БД хранят плейлисты/

### Дзен: глубина пагинации и has_more

Без пользовательской сессии: первая страница честная,
`has_more` — только когда страница переполнена. Мало видео +
`has_more: false` → догрузить нельзя. Рычаги на бэке:
больший лимит первой страницы, `has_more` по признаку
продолжения, сессионная цепочка. Актуально в свете решения
«Дзен первым источником» в видео-табе.

### Видео-плейлисты и иконки ресурса

Простыми словами: VK и YouTube умеют плейлисты из роликов —

### Presence устройств на сокетах вместо heartbeat

Уведомление о подключении второго устройства сейчас приходит
только при логине (APK на телефоне включился — устройства не
видно, пока не перелогинишься). Инфраструктура на сокетах
есть: `playback.device.connected/disconnected` уже летят всем
устройствам юзера — connect/disconnect виден мгновенно.

Направление (решение 2026-11-27): heartbeat POST раз в 30 с
убираем, presence держим на сокетном соединении — та же
логика, что у онлайн-детекта вместо health. Открытые детали
для бэк-агента:
- Маппинг сокет↔device_uuid: приватный канал аутентифицирует
  юзера, но не устройство — нужен claim (device_uuid в auth
  handshake или одноразовая привязка после connect).
- Грейс перед «устройство офлайн» (30–60 с): иначе флап сокета
  дёрнет presence, как дёргал зонд.
- Регистрация устройства (POST /devices — имя, тип) остаётся:
  heartbeat удаляем, создание записи — нет.
- Фон: ConnectionService держит сокет, presence в фоне живёт;
  Doze убил процесс → сокет мёртв → офлайн честный.

### Обложки видео-плиток: клиентский lazy-load

Уточнение темы: речь не о серверном кеше ютуб-обложек, а о
клиенте. Превью видео идут через прокси `/yt-resource/cover`
(туннель в NL) — список/плитки из десятков роликов тянут
каждый скролл заново, с прокси-латентностью. Дёшево на фронте:
`loading="lazy"` + кеш WebView (проверить, что прокси отдаёт
кешируемые заголовки) + при необходимости небольшой
персистентный клиентский кеш. Без бэка. Актуально для
видео-плиток реформы поиска и вкладки видео в избранном;
волна сюда не относится (аудио, обложки Яндекса).
