# Видео (режим клипов) — решения и план

Статус: **Дзен-источник реализован (Laravel + микросервис
dzen_resource); YouTube-источник реализован и проверен живьём
(2026-11-24): egress — desync (byedpi) с residential IP хоста,
VPN не используется вообще; персональные cookies пользователей
(база → X-YT-Cookies), PO-токены, HLS-контракт (лесенка до
2160p) — поиск/потоки/relay отдают реальные данные; фронт —
позже. VK отклонён: бизнес-верификация неприемлема для
полупиратского приложения.**

## Словарь

Видео — полноправный тип семейства снапшотов (`SnapshotTypeEnum::VIDEO`),
не «клип»-производное. «Клипы» остались только названием режима в плеере.
Словарь платформы см. в AGENTS.md («трек» — только аудио-снапшот;
смешанные коллекции — «item»/«snapshot»; аудио-операции — «audio»).

## Принятые решения

1. **Свой плеер поверх прямых ссылок.** Embed-плеер отвергнут
   (реклама и брендинг YouTube внутри нашего UI).
2. **Официальный Data API v3 YouTube отвергнут** (квоты, нет ссылок
   на потоки). Проверено из РФ: доступен только `www.googleapis.com`,
   вся видео-инфраструктура YouTube заблокирована (DNS подавлен,
   TLS к google-диапазонам глушится).
3. **Основной будущий источник — VK Видео.** Официальный API из РФ
   без VPN (`api.vk.com` проверен): `video.search` + `video.get`
   (метаданные + прямые mp4 в `files`). Авторизация — OAuth
   access_token standalone-приложения (как токен Яндекс Музыки).
   Ссылки не привязаны к IP → прокси потока не нужен. Минусы: каталог
   меньше ютубовского, у части видео `files` пустой, матчинг
   ранжируем сами (дельта длительности, просмотры, эвристики
   названия/канала). Месячная квота кабинета VK ID (10k вызовов
   без верификации) на видео-only нагрузку с кэшем хватает;
   схемы обхода/эскалации зафиксированы в обсуждении.
   **Отклонён (2026-11-24):** регистрация приложения VK теперь
   требует бизнес-аккаунта/верификации — для полупиратского
   приложения неприемлемо (его не светим). Видео-источники —
   Дзен и YouTube.
4. **YouTube — второй источник (реализован 2026-11-24).**
   Egress — **desync (byedpi) с residential IP хоста, VPN не
   используется вообще**: дата-центровый ASN (туннель HMN,
   коммерческие VPN — проверено 42 конфига) деградировал выдачу
   до 360p независимо от cookies/PO-токенов. Residential IP +
   desync снимает и блокировку РФ (ТСПУ обходится фрагментацией
   TLS), и деградацию YouTube. Ссылки на потоки IP-bound →
   прокси потока через микросервис обязателен. Программного
   логина у yt-dlp для YouTube нет; cookies пользователей —
   опциональный эшелон (на residential нужны редко).
5. **Поисковый запрос на проводе не участвует.** Фронт шлёт
   трек-снапшот, материал для матчинга — title/artists/duration_ms
   внутри него. Контракт устойчив к смене/добавлению источника.
6. **Дзен — первый реальный источник (вместо мока).** Публичный
   контент, без ключей и квот; микросервис ходит на dzen.ru как
   браузер (анонимная цепочка редиректов dzen → sso.passport →
   login.vk.com → retpath), парсит встроенный JSON страниц.
   Потоки — прогрессивные mp4 с CDN okcdn, но CDN требует Referer
   и сессионную куку (ставится master-запросом m3u8) → браузеру
   недоступен, байты идут через relay микросервиса
   (nginx-локация `/dzen-resource/`). Мок (MockVideoService,
   кейс `SnapshotSourceEnum::MOCK`) удалён вместе с заменой.

## Дзен-источник (реализован)

```
POST /api/v1/skyfy/videos/resolve   (auth:sanctum, throttle 60/мин)
  тело: трек-снапшот
  ответ: { video: VideoSnapshot, streams: [{quality, url}], ttl_sec }

POST /api/v1/skyfy/videos/get-url   (auth:sanctum, throttle 120/мин)
  тело: видео-снапшот (type=video)
  ответ: { streams: [{quality, url}], ttl_sec }
```

Цепочка: роут → `VideoController` → экшены `ResolveVideo` /
`GetVideoStreams` → `DzenVideoResource` (оба контракта:
`VideoServiceContract` + `SearchResourceContract`,
`App\Domain\Infrastructure\External\Dzen`) → микросервис
`dzen_resource` (FastAPI, репозиторий рядом с `yandex_music`,
сервис `sky-fi-dzen-resource`, порт 8002). Эндпоинты
микросервиса: `GET /search?q&page&limit`, `GET /video/{id}`,
`GET /video/{id}/streams`, `GET /video/{id}/stream?type=N`
(relay mp4 чанками, Range прокидывается). Резолв — стартовая
эвристика: поиск «исполнители — название» из трека, первый
результат; ранжирование (дельта длительности, канал, просмотры)
— отдельной задачей, контракт не затронет.

URL потоков, которые бэк отдаёт фронту, — публичный relay:
`{host}/dzen-resource/video/{id}/stream?type={код_качества}`
(nginx проксирует на микросервис, PHP байты не трогает).
Коды качества — лестница okcdn: 0=240p, 1=360p, 2=480p,
3=720p, 5=1080p (дефолт relay-запроса — 3).

Поиск: `DzenVideoResource` зарегистрирован в реестре
`SearchMusicService` строкой вместо мока. Секция `videos`
поискового ответа всегда присутствует: аудио-источники отдают
её пустой, Дзен наполняет результатами — элементы помечаются
is_favorite наравне с аудио, склейка идёт через тот же
`merge()`. Источник снапшотов — `SnapshotSourceEnum::DZEN`,
source_id — id ролика из URL Дзена.

Ограничения поиска (проверено 2026-11-23): анонимная выдача —
один блок ~20 item'ов со вкладки «Видео» (`type_filter=video,
short`; дефолтная «Всё» смешивает статьи и даёт 4 видео).
Курсора продолжения у SSR нет: параметр page Дзен игнорирует
(каждый запрос случайно вертит один пул ~20–30 роликов),
поэтому страниц больше нет — page>1 отдаёт честный пустой
ответ, has_more ставим только когда блок больше запрошенного
limit. Внутренний `/portal/dzensearch/desktop` без JS-сессии
не раскопан — настоящая пагинация возможна только с
пользовательской сессией, сознательно не делаем. Антибот Дзена
при сериях быстрых повторов начинает отдавать пустой каркас
страницы (признак: в HTML нет строки запроса) — микросервис
детектирует, ретраит с паузой и честно падает в 502, если
каркас стоит. Watch-страницы и CDN-потоки этим гейтом не
затрагиваются: get-url и потоки работают стабильно.

Проверено живьём (разведка 2026-11-23): поиск и watch-страницы
отдают полные item'ы (метаданные + потоки) во встроенном JSON;
master m3u8 отдаётся только с `Referer: https://dzen.ru/` и
открывает сессию (кука `tstc`), с ней прогрессивные mp4
отдаются с рабочим Range (206, перемотка идёт).
yt-dlp для Дзена не нужен (экстрактор хрупкий, поиска у него
нет — всё берём из страниц напрямую).

`VideoSnapshot`: конверт + `duration_ms` (своя длительность),
`artists` (канал/студия/владелец, может быть пусто — фильмы),
`cover_url`, `watch_url` (постоянные поля). Потоков в снапшоте
нет — только временные через `videos/get-url`. Элементы очереди
и плейлистов принимают видео-снапшоты наравне с треками;
`current_snapshot` плеера — любой тип.

## YouTube-источник (реализован 2026-11-24, desync-egress)

Шаблон — дзен-микросервис: тот же контракт эндпоинтов, тот же
relay. Egress — **desync (byedpi) с residential IP хоста, VPN не
используется вообще** (до 2026-11-24 был AmneziaWG-туннель HMN —
выпилен: дата-центровый ASN деградировал выдачу до 360p, история
в docs/youtube-account-care.md). Потоки googlevideo IP-bound
(под IP хоста) → браузер играет только relay-ссылки.

Инфраструктура (реализовано):
- Один контейнер `sky-fi-youtube-resource` (FastAPI, порт 8003):
  supervisord держит четыре процесса — dnsproxy (DoH-резолвер,
  127.0.0.1:53), ciadpi (desync SOCKS5, 127.0.0.1:1080), bgutil
  POT-сервер (127.0.0.1:4416) и uvicorn.
- **DNS — DoH** (dnsproxy → `https://1.1.1.1/dns-query`,
  `--ipv6-disabled --cache`): системный резолв из РФ для
  google-диапазонов подавлен (DNS-подмена ТСПУ), DoH через
  1.1.1.1 работает без обхода. Резолвер контейнера —
  `dns: 127.0.0.1` в compose.
- **Desync** (byedpi/ciadpi, сборка из исходников, пин тега):
  фрагментация TLS-записей + подмена SNI — ТСПУ провайдера
  соединение не распознаёт и не режет. Стратегия — env
  `BYEDPI_ARGS` (дефолт — рецепт ByeByeDPI, проверенный на
  провайдерах РФ; под конкретного провайдера подбирается zapret
  blockcheck'ом). Через прокси идёт весь YouTube-трафик:
  yt-dlp (`proxy` в opts), httpx relay/манифесты/обложки
  (`YT_PROXY`), bgutil (`HTTPS_PROXY` — deno читает).
- Healthcheck контейнера: curl generate_204 через SOCKS-прокси —
  покрывает всю цепочку (DNS + desync) разом.
- nginx-локация `/yt-resource/` — без изменений. URL потоков для
  фронта: `{host}/yt-resource/...` — фронт открывает только наш
  хост, обход ему не нужен.
- Cookies — только персональные файлы пользователей из базы
  (общего fallback-файла нет): бэк шлёт содержимое заголовком
  X-YT-Cookies (base64), микросервис материализует его в /tmp
  по sha256-хешу (файл живёт сутки после последнего обращения;
  yt-dlp при закрытии перезаписывает cookiejar — поэтому файл
  и материализуется, а не маунтится). Relay-ссылки потоков несут
  тот же хеш параметром ch (браузеру заголовок не прикрепить).
  Лимит заголовков uvicorn поднят
  (`--h11-max-incomplete-event-size 262144`): base64 файла до
  ~90 КБ, дефолтных 16 КБ h11 не хватает.

Резолв: yt-dlp как Python-библиотека, **строго один player_client**
(несколько значений НЕ объединяют форматы и не дают фолбэк —
yt-dlp берёт первый успешный по своему приоритету, android
перекрывает tv_embedded и отдаёт деградированные 360p). Без куки —
tv_embedded (полная лесенка: HLS-манифест до 2160p + https-файлы
DASH-качеств), при его поломке — фолбэк android (прогрессив
360p); с куки — web_embedded (HLS-лесенка и принимает куки;
дефолтный web переведён YouTube на SABR — прямых URL в player
response нет вообще). Сигнатуры/n-challenge решает Deno
(EJS: yt-dlp[default] тащит пакет yt-dlp-ejs, deno 2.9.8 в
образе, пин в Dockerfile). Поиск — плоский extract
(extract_flat: карточки без плеерных страниц каждого результата);
пагинация — «первые N»: страница N запрашивает первые N×limit
записей (yt-dlp сам ходит по continuation-страницам YouTube,
произвольного доступа к странице нет) и отрезает свой срез.
Выдача кэшируется по запросу 30 мин с заморозкой префикса:
выдача YouTube нестабильна между fetch'ами (ролики переезжают
на 1–2 позиции), поэтому дотяжка только дополняет кэш новыми
id — иначе страницы плывут и дублируются. Потолок глубины —
200 роликов на запрос. Метаданные/потоки — полный extract
с кэшем 30 мин (перемотка
не дёргает yt-dlp повторно). PO-токены (proof-of-origin)
обязательны независимо от IP: без них player response
деградирован (только прогрессив 360p у всех клиентов) —
bgutil-провайдер живёт внутри контейнера (supervisord,
127.0.0.1:4416, egress через тот же desync-прокси), плагин
bgutil-ytdlp-pot-provider==2.0.2, версии сервера и плагина
пиним одинаковыми. Детект «Sign in to confirm» → 502 с честным
текстом.

Контракт (копия дзена): `GET /search?q&page&limit`,
`GET /video/{id}`, `GET /video/{id}/streams`,
`GET /video/{id}/stream?itag=N` (relay с Range, без itag —
максимальное качество). HLS: `GET /hls/{id}/manifest.m3u8?ch=`
(variant-манифест, вложенные ссылки переписаны в relay) и
`GET /hls-seg?u=` (плейлисты — с rewrite ссылок, сегменты —
через дисковый кеш микросервиса; URL переносятся байт-в-байт —
перекодирование ломает подпись, CDN отвечает 403). Плюс `GET /cover?u=` —
прокси обложек с YouTube-CDN (i.ytimg.com/ggpht): картинки из
РФ без обхода не открываются, хосты ограничены allowlist'ом.
Бэк переписывает cover_url youtube-снапшотов в
`/yt-resource/cover?u=...` (`CoverProxy`) — относительным
путём, активную базу подставляет клиент (api.md §1.7);
nginx-локация /yt-resource/ уже есть — после правок конфига
nginx нужен reload/restart контейнера. Снапшоты —
`SnapshotSourceEnum::YOUTUBE`, source_id — id ролика
(watch-URL `https://www.youtube.com/watch?v={id}`).

Laravel-сторона (реализовано): `YoutubeVideoResource` (аналог
`DzenVideoResource`, оба контракта), регистрация в реестре
поиска; резолв — YouTube, поисковая строка «исполнитель —
название official» (Дзен-фолбэк в `ResolveVideo` временно
закомментирован), get-url диспатчит по источнику снапшота
(`GetVideoStreams`). Ответ get-url: `{streams, ttl_sec, hls}` —
`hls.manifest_url` ведёт на наш relay (тот же ch, что у потоков),
относительным путём (клиент подставляет базу, api.md §1.7);
аудиодорожки (дубляжи) и субтитры внутри манифеста (EXT-X-MEDIA),
отдельного поля в контракте нет — фронт читает их hls.js.
Инструкция фронту (hls.js) — api.md §8.1. Тесты: 17 зелёных на
search/resolve/get-url/cookies.

Проверено живьём (2026-11-24, residential egress + desync):
поиск отдаёт реальные item'ы; tv_embedded + POT — полная
HLS-лесенка до 2160p (без POT — только 360p у ВСЕХ клиентов,
это не деградация IP, а общий гейт YouTube); VEVO-клипы
(Despacito) — полная лесенка без кук (на DC-IP были под стеной
«Sign in to confirm»); цепочка manifest → playlist → segment
через relay и через nginx — 200, прогрессивный relay — 206,
обложки — 200. Важный нюанс residential-RF egress: региональные
блоки правообладателей (SME и т.п.) теперь действуют на нас как
на любого РФ-зрителя — часть зарубежных клипов недоступна
(на DC-IP Нидерландов их не было). Это честная цена бесплатного
egress; обход — те же персональные cookies с не-RU аккаунтом
либо Дзен-фолбэк в резолве.

Кеш HLS-сегментов (реализован 2026-11-24, по замерам с фронта):
холодный сегмент googlevideo отвечает первым байтом через
секунды — edge тянет слайс с origin, конкурентные холодные
слайсы встают в очередь origin-pull'а (замерено: 4 параллельных
холодных 2160p — TTFB 1–11 с при теле на ~11 МБ/с; это НЕ
буферизация нашего стека и НЕ троттлинг полосы — `ratebypass=yes`
в ссылках, тёплый сегмент — TTFB 0.04 с). Дефолтный таймаут
TTFB hls.js (10 с) такие сегменты обрывал, и каждый ретрай
начинал origin-pull заново — без кеша сегмент не докачивался
никогда. Поэтому в микросервисе сегменты без Range идут через
дисковый кеш (`hls_cache.py`): скачка — фоновая таска,
не зависящая от обрывов клиента; параллельные/повторные запросы
делят одну апстрим-скачку и читают растущий файл; после коммита —
файл с диска мгновенно (`X-Cache: hit|fill|wait`,
`Cache-Control: max-age=3600` для браузерного кеша). TTL 3 ч,
лимит 2 ГБ LRU, ≤8 параллельных скачек (env
`YT_HLS_CACHE_*`/`YT_HLS_FILL_CONCURRENCY`). Фронту: таймаут
TTFB поднимать до ~30 с (уже сделано, hls-engine.ts) — холодный
high-itag первый раз реально ждёт origin-pull; повторные
обращения — мгновенные. Попутно починен класс отказов сегментов:
edge без слайса отвечает 302 на соседний узел (mm/mn-фолбэки
ссылки) — relay теперь проходит редиректы сам (≤3 хопов с
проверкой по allowlist), раньше падал 502.

Персональные cookies (реализовано 2026-11-24): у каждого
пользователя — свой Netscape-файл (`POST /videos/youtube-cookies`,
см. api.md), хранится в базе зашифрованным (Crypt, APP_KEY),
в микросервис уходит заголовком X-YT-Cookies (base64) и там
материализуется в /tmp по sha256-хешу; relay-ссылки потоков
несут тот же хеш параметром ch — браузеру заголовок не
прикрепить. Общего fallback-файла нет: без личного файла
запросы идут без куки. Эндпоинты: загрузка/статус/удаление.
Кэш метаданных микросервиса ключается с учётом куки.
Инструкция для пользователей — docs/youtube-cookies.md;
сопровождение аккаунтов и эшелоны обхода антибота (ops) —
docs/youtube-account-care.md.

Осталось:
1. Ротация аккаунтов, алерты на 502 — сопровождение.
2. Подбор desync-стратегии под провайдера при смене хоста
   (zapret blockcheck; стратегия — env BYEDPI_ARGS).

Видео-источники — Дзен (из РФ без обхода, реализован) и YouTube
(desync-egress без VPN, cookies, PO-токены, HLS-контракт до
2160p — реализован и проверен живьём).
VK отклонён (2026-11-24): регистрация приложения требует
бизнес-аккаунта/верификации VK ID — приложение не светим.
Это arms race: регулярное сопровождение, а не разовая фича —
прецедент эксплуатации такого: дзен-микросервис.

## Фронт (план, проекта пока нет)

Фронт с нуля, первый потребитель — режим клипов: глобальный тоггл
в плеере → при смене трека `videos/resolve` → свой `<video>`-плеер
со списком `streams` и выбором качества (старт — 720 или авто).
Тоггл — не локальная настройка, а часть состояния плеера:
`clips_enabled` в `state`, переключается через
`PATCH /player/options` и приезжает бродкастом на все устройства
(иначе рассинхрон: одно играет видео, другое — аудио).
Состояния: resolving, видео не найдено (остаёмся на аудио),
ошибка потока → фолбэк на аудио; `watch_url` — всегда. Кэш резолва
по паре (source_type, source_id) в сторе. Единый десериализатор
снапшота на все типы; нативным клиентам (Android ExoPlayer,
десктоп) — тот же контракт, plain URL в плеер.

## Матчинг «трек → видео» (для реального источника)

Топ-N поиска по «исполнитель — название» + ранжирование:
сообщество/канал совпадает с исполнителем (verified), длительность
в разумной дельте от длительности трека, просмотры. Слово
«official» в запросе — слабый фильтр. Связь «трек → видео»
кэшируется навсегда (идентификатор видео стабилен).

Нюанс из старого обсуждения: авто-сгенерированные каналы
«Artist - Topic» на YouTube содержат оригинальное аудио с точной
длительностью — не клипы (статичная обложка), но полезны как
отдельный режим матчинга «воспроизведение с YouTube без
расхождения длительности».
