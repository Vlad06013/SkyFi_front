# Предложение бэку: обновление APK через `/app-updates`

Дата: 2026-11-28. Автор: фронт-агент. Статус: предложение, ждёт
реализации на бэке. После реализации `api.md §19` и `contracts.md`
правит бэк-агент (каноничные копии), фронт подтягивает зеркало.

## Зачем

Нативная оболочка (APK) сейчас распространяется руками: Telegram,
GitHub raw. Хотим, чтобы тот же механизм обновлений, что качает
веб-бандлы (OTA), сообщал и о новой оболочке: приложение видит оффер,
скачивает APK и отдаёт его системному установщику Android. OTA-бандлы
продолжают работать без изменений.

## Принцип

Один эндпоинт `GET /app-updates/check` отвечает на два вида
обновлений; вид оффера — в поле `kind`. Совместимость в обе стороны:

- старый клиент + новый бэк: клиент не шлёт параметр `apk` — бэк
  никогда не отдаёт ему `kind: 'apk'` (старый клиент попытался бы
  поставить APK как ZIP-бандл);
- новый клиент + старый бэк: в ответе нет `kind` — клиент считает
  оффер бандлом.

## Изменения API

### `GET /app-updates/check`

Новый необязательный query-параметр `apk` (`apk=1`): клиент сообщает,
что умеет принимать офферы оболочки. Без него поведение эндпоинта
не меняется вообще.

В `data` добавляется поле `kind: 'bundle' | 'apk'`. Слать его можно
всегда (лишнее поле старых клиентов не ломает), но `kind: 'apk'`
допустим только в ответе на запрос с `apk=1`.

Правило выдачи при `apk=1`:

1. Если есть релиз оболочки с `version` > `shell` из запроса
   (semver, `version_compare` — как для бандлов) — вернуть оффер
   оболочки `kind: 'apk'`, даже если есть и более новый бандл:
   APK несёт свежий бандл внутри, а после установки оболочки
   следующий check предложит бандл, если тот ещё новее.
2. Иначе — существующая логика бандла (включая фильтр
   `shell_min_version`).

Форма `data` для оболочки — та же, что у бандла:

| Поле | Значение для APK |
|---|---|
| `kind` | `'apk'` |
| `version` | версия оболочки `X.Y.Z` (`versionName`) |
| `url` | подписанная ссылка на APK (без токена, живёт 60 мин) |
| `sha256` | SHA-256 файла (hex) |
| `size_bytes` | размер файла |
| `mandatory` | обязательное: диалог без «Позже» |
| `notes` | заметки релиза или `null` |

Пример ответа:

```json
{
  "errors": null,
  "data": {
    "kind": "apk",
    "version": "1.1.0",
    "url": "http://192.168.1.10:8080/api/v1/skyfy/app-updates/download-apk/3?expires=…&signature=…",
    "sha256": "9f2c…",
    "size_bytes": 23456789,
    "mandatory": false,
    "notes": "Плагин установки APK"
  }
}
```

### Скачивание APK

Подписанный роут по образцу `GET /app-updates/download/{id}` (можно
тот же роут, если релизы лежат в одной таблице): отдаёт файл без
токена, ссылка живёт 60 минут и строится от адреса запроса (как все
ссылки, api.md §1.7). Заголовки:

- `Content-Type: application/vnd.android.package-archive`
- `Content-Disposition: attachment; filename="SkyFi-<version>.apk"`

### Команда публикации

По образцу `app:release`:

```sh
php artisan app:release-apk <path-to.apk> <version> [--mandatory] [--notes="…"]
```

Копия файла в `storage/app/app-releases` (или рядом), sha256, размер,
запись в БД. Повтор той же версии — 409. Хранение — на усмотрение
бэка: та же таблица релизов с колонкой `kind` или отдельная таблица;
контрактно важен только ответ `check`.

### `scripts/release-apk.sh`

После сборки — шаг регистрации (зеркально `release-ota.sh`):
`docker exec … php artisan app:release-apk <apk> <versionName>`
с версией из `versionName` в `android/app/build.gradle`. Полезен
флаг `--no-publish` для локальной сборки без публикации.

## Поведение клиента (для понимания)

- `kind` отсутствует или `'bundle'` → текущий OTA-флоу
  (`@capgo/capacitor-updater`).
- `kind: 'apk'` → диалог «Обновить приложение до X.Y.Z?». По
  «Обновить» клиент открывает `url` вне WebView (глав-frame
  навигация на чужой хост уходит в системный `ACTION_VIEW`):
  ссылку забирает браузер, качает APK, пользователь подтверждает
  установку штатным установщиком. Обновление встаёт поверх при
  совпадении подписи пакета — подпись проверяет сам Android.
- Шаг 2 (отдельным APK, позже): скачивание внутри приложения через
  `@capacitor/filesystem` с прогрессом + install intent
  (`REQUEST_INSTALL_PACKAGES`). Для него в оффере уже есть
  `sha256`/`size_bytes` — тогда клиент будет сверять хеш сам.

## Ограничения и заметки

- Подпись: APK обновляет только APK с той же подписью
  (debug-keystore машины сборки). Смена машины/keystore — ручная
  переустановка с потерей данных приложения.
- `versionCode` должен расти от релиза к релизу — `release-apk.sh`
  это уже делает.
- `mandatory` для APK: диалог без «Позже», но факт установки клиент
  не проверяет — если оболочка осталась старой, оффер повторится при
  следующем check.
- Уже установленный OTA-бандл обновление оболочки не затирает:
  данные приложения сохраняются, бандл продолжает работать.
