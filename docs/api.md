# SkyFi API — контракт для фронта

Три документа — одна система: `api.md` (контракт),
`contracts.md` (TypeScript-типы и мок-фикстуры 1:1),
`frontend.md` (требования к фронту). Правило дрейфа:
сначала api.md, потом contracts.md, потом фронт.

Единственный источник правды о бэкенде. После этого документа
в код бэка лазить не нужно. Бэк: Laravel, все ответы в единой
обёртке, сущности на проводе — только снапшоты.

- Актуальность: синхронизирован с кодом вручную, при изменении
  API сначала правится этот документ.
- Базовый URL: `/api/v1/skyfy`
- Окружения: dev — `http://<хост>:<порт>` (см. compose), prod — тот
  же домен, что и вебсокеты (см. «Сокеты»).
- Адрес бэка — настройка клиента: у устройства может быть свой
  адрес (ТВ дома — LAN, магнитола — внешний и т.п.). Все
  абсолютные ссылки в ответах (обложки, стримы, relay) бэк
  строит от того адреса, на который пришёл запрос, — поэтому
  любой рабочий адрес даёт консистентные ссылки, ничего
  переконфигурировать на бэке не нужно.

## 1. Общие конвенции

### 1.1. Обёртка ответа

Каждый JSON-ответ:

```json
{ "errors": null, "data": {}, "pagination": null }
```

- `errors: null` — успех. Иначе строка или объект ошибок
  (`{"поле": ["сообщение"]}` при 422).
- `data` — полезная нагрузка (объект, массив или null).
- `pagination` — объект пагинации или null:
  `{ current_page, last_page, per_page, total }` (номерная,
  параметры `page` / `limit`).

Коды: 200 ок, 201 создано, 401 нет/просрочен токен, 404 нет
сущности (сообщение в `errors`), 422 валидация (ошибки полей
в `errors`), 429 троттлинг, 5xx бэк/внешние сервисы
(502/503 с человекочитаемым сообщением).

### 1.2. Авторизация

Sanctum Bearer-токен: `Authorization: Bearer <token>`.
Токен выдаётся при register/login/QR-входе (`token`,
`plainTextToken` внутри `data`). Все роуты требуют токен,
кроме: register, login, forgot/reset-password, qr-login
(store/show), health.

### 1.3. Троттлинг

Чувствительные роуты ограничены (указано у каждого). При 429 —
показать тост и не ретраить мгновенно.

### 1.4. Health (без авторизации)

`GET /health` (под базовым префиксом, фактически
`/api/v1/skyfy/health` — голый `/health` отдаёт 404) →
`{ status: "ok", server_time }`. Служит
офлайн-детекту: неуспешный запрос = бэк недоступен (сеть есть —
иначе fetch не ушёл бы; токен не при чём, auth тут нет).

### 1.5. Словарь платформы

- **snapshot** — любая сущность на проводе; дискриминатор
  `type`; идентичность — пара `source_type` + `source_id`.
- **item** — элемент смешанных списков (очередь, плейлист,
  избранное): snapshot любого типа.
- **track** — только аудио; **video** — видео (клипы, фильмы).
- Источники `source_type`: `yandex_music`, `upload`,
  `skyfi` (свой каталог), `dzen`, `youtube`.

### 1.6. Эхо-поля команд

Каждый мутирующий роут плеера/очереди/устройств принимает:

- `origin_device_id` — постоянный UUID устройства-инициатора
  (`device_uuid`: клиент генерирует при первой регистрации
  устройства, `POST /player/devices`; совпадает с
  `devices[].device_uuid`). Устройство-инициатор глушит эхо
  своих же команд по этому полю. Эхо-поля всегда телом команды,
  включая DELETE.
- `command_id` — uuid команды, генерирует клиент на каждую
  команду; дедупликация повторных доставок.

Исключение — команды по чужой очереди
(`POST /friends/{id}/queue`, reorder друга): эхо-полей нет,
инициатор — другой пользователь.

### 1.7. Ссылки на ресурсы бэка (относительные URL)

Устройства ходят на бэк по разным адресам (LAN, внешний IP),
а бэк не знает, из какой сети читатель — особенно в сокетах,
где один пейлоад уходит всем устройствам сразу. Поэтому **все
ссылки на собственные ресурсы бэка отдаются относительными
путями** — начинаются с `/`, без хоста:

- обложки-прокси `/yt-resource/cover?u=…` (YouTube);
- видеопотоки `/yt-resource/…`, `/dzen-resource/…`
  (`videos/get-url`, `videos/resolve`: `streams[].url`,
  `hls.manifest_url`);
- поток загрузки (`audio/get-url` для upload) — наш
  авторизованный эндпоинт;
- аватар `/storage/avatars/…`, обложка плейлиста `/storage/…`.

Правило клиента одно, без списка полей: любую строку-ссылку из
ответа API или пейлоада сокета прогонять через резолвер в точке
использования (img src, источник плеера, URL манифеста):

```ts
const resolveUrl = (url: string): string =>
  url.startsWith('/') ? activeBase + url : url;
```

`activeBase` — та же база (хост:порт), по которой клиент ходит
в API. Внешние http(s)-ссылки (обложки Яндекса/Дзена,
`stream_url` archive.org, `watch_url`) проходят резолвер без
изменений — ветвиться по полям не нужно. Сегменты внутри m3u8
трогать не надо: плеер резолвит их от origin URL манифеста,
который уже с правильной базой.

Обратная совместимость: бэк принимает и абсолютные ссылки со
своими хостами (LAN/внешний IP/APP_URL) — обрезает их до пути
при приёме снапшотов, старые клиенты не ломаются.

## 2. Снапшоты

Общий конверт (все типы): `type`, `source_type`, `source_id`,
`title`, `artists: [{name, source_id?}]` (исполнители/авторы,
может быть `[]`). Проверено: у artist-снапшотов поле `artists`
не приходит (ни в поиске, ни в избранном) — фронт от него не
зависит, подзаголовок строки артиста фиксированный.

- **track**: + `duration_ms|null`, `album {title?, year?,
  cover_url?, source_id?}|null`, `cover_url|null` (собственная
  обложка трека; null — фолбэк на `album.cover_url`), `lyrics|null`
  (на проводе не приходит — отдельный роут), `stream_url|null`
  (постоянная ссылка, только у источников со стабильными URL; у
  Яндекса всегда null), `sort|null` (вес позиции: больше = выше
  во вкладке).
- **video**: + `duration_ms|null`, `cover_url|null` (постер),
  `watch_url|null` (постоянная страница в источнике — кнопка
  «оригинал», шаринг; не для воспроизведения), `sort|null`.
- **album**: + `year|null`, `cover_url|null`, `track_count|null`.
- **artist**: + `cover_url|null`.
- **playlist**: + `owner_name|null`, `cover_url|null`,
  `item_count|null`.

Правила: ссылки на потоки (audio/video) с TTL в снапшоты не
входят — выдаются отдельными роутами по паре
`(source_type, source_id)`. `type` ∈ `track|video|album|
playlist|artist`. `cover_url`/`stream_url` на ресурсы бэка —
относительные пути (§1.7).

## 3. Авторизация и профиль

| Метод/путь | Тело → Ответ |
|---|---|
| `POST /register` (6/мин) | `{name, email, password, password_confirmation}` → `user, token` |
| `POST /login` (6/мин) | `{email, password}` → `user, token` |
| `POST /forgot-password` (6/мин) | `{email}` → сообщение; письмо с кодом |
| `POST /reset-password` (12/мин) | `{email, code, password, password_confirmation}` |
| `GET /user` | → `user` (профиль текущего) |
| `POST /logout` | → сообщение; токен отзывается |
| `PATCH /profile` | `{name?}` |
| `PUT /profile/avatar` | multipart `avatar` (image) |
| `DELETE /profile/avatar` | → дефолтный аватар |

Форма `user` в register/login/`GET /user`: `{id, name, email,
avatar_url}`. QR-поллинг при confirmed отдаёт полную модель
(лишние поля `email_verified_at`, `avatar`, `created_at`,
`updated_at`) — фронту нужны те же `id/name/email/avatar_url`.

**QR-вход** (для ТВ/магнитолы):
- `POST /qr-login` → `data: {code, expires_at, qr_svg}` — код,
  абсолютный срок (ISO 8601 UTC, ~15 мин) и готовый QR в SVG.
  Фронт рендерит `qr_svg` как есть, сам QR не генерирует.
- ТВ поллит `GET /qr-login/{code}` → `data: {status, token, user}`:
  `pending` — `token`/`user` null; `confirmed` — полные `token` +
  `user`, ими и логинимся; нет кода — 404 «QR-код не найден.».
- Телефон (auth): `POST /qr-login/confirm` `{code}` → 200
  `{status: "confirmed"}`; без токена — 401 «Не авторизован.».

**Яндекс Музыка (аккаунт)**:
- `POST /yandex-music/auth/device/start` (12/мин) →
  `data: {session_id, status: "pending", verification_url,
  user_code}` — старт device flow (пользователь вводит код на
  странице Яндекса). Идемпотентен: при активной сессии
  возвращает её (тот же код/ссылку). Сервис Яндекса может
  отдать `verification_url`/`user_code` = null — тогда код и
  ссылку подхватывает поллинг статуса.
- `GET /yandex-music/auth/device/status` (30/мин) — одновременно
  поллинг сессии и проверка «подключён ли аккаунт»:
  `data: {status, connected, verification_url?, user_code?,
  message?}`. `status`: `not_started` (сессии нет; `connected` —
  сохранён ли токен), `pending` (сессия жива, поля кода/ссылки
  заполнены), `connected` (токен одноразово забран и сохранён
  только на сервере; сессия удалена), иначе (`expired`/`failed`/
  `consumed`/др.) — сессия умерла без подключения и удалена.
- `DELETE /yandex-music/auth` → `data: {connected: false,
  message}` — отключить аккаунт (токен и сессия удаляются).
  Не подключён → волна/импорт недоступны (эндпоинты отдадут
  4xx с сообщением).

## 4. Устройства (`/player/devices`)

Приложение при старте регистрирует устройство со своим
`device_uuid` (постоянный UUID клиента) и дальше адресуется
только по нему: `{device}` в путях, `origin_device_id` в телах
команд и `active_device_id` в состоянии плеера — это всегда
`device_uuid`, int-id устройств на провод не уходит.

Presence — на сокетах: устройство после коннекта подписывается
на свой приватный канал `device.{uuid}` (см. §17); подписка =
онлайн (`is_online: true`, бродкаст `playback.device.connected`
на переходе), разрыв = офлайн после грейса 60 с без
переподключения (бродкаст `playback.device.disconnected`;
краткий флап сокета молчит — ни connected, ни disconnected).
Heartbeat (`POST /devices/heartbeat`) — опциональный запасной
признак: фронт его не шлёт, но пока приходит, тоже держит
онлайн (`is_online` = живой сокет ИЛИ свежий heartbeat).

Потеря активного устройства останавливает воспроизведение:
у активного нет ни живого сокета (разрыв, грейс 60 с прошёл без
переподключения), ни свежей отметки heartbeat (порог 90 с,
подстраховка планировщиком раз в минуту) — бэк сам
ставит стейт в stop (`is_playing: false`, позиция сохраняется),
обнуляет `active_device_id` и шлёт `playback.state.updated` со
свежей `version`. Авто-выбора нового активного и
авто-возобновления нет: play с любого устройства сам делает его
активным. Признака «активности» у самого устройства нет —
активное определяется только `active_device_id` состояния.

| Метод/путь | Тело → Ответ |
|---|---|
| `GET /` | → `{devices: [{device_uuid, name, type, last_seen_at, is_online}]}` (только онлайн; presence-модель) |
| `POST /` (30/мин) | `{name, type: phone\|computer\|car\|tv, origin_device_id: uuid, command_id}` → устройство; повторная регистрация по тому же uuid обновляет профиль |
| `PATCH /{device}/activate` (30/мин) | `{origin_device_id, command_id}` → это устройство — активное (играет); `{device}` в пути — `device_uuid` |
| `POST /player/devices/heartbeat` (120/мин) | `{origin_device_id: uuid}` → `{message: "ok"}` — продлить presence; неизвестный uuid — 404 |
| `DELETE /{device}` | тело `{origin_device_id, command_id}` → удалить; `{device}` в пути — `device_uuid` |

## 5. Плеер (`/player`)

Модель: сервер — источник истины. Любая команда с любого
устройства → сервер → бродкаст → остальные устройства
применяют; инициатор глушит эхо (см. «Сокеты»).

**Состояние** (`GET /player`):
`{ state: { id, current_snapshot|null, position_seconds,
is_playing, repeat_mode: off|one|all, shuffle_enabled,
clips_enabled, version,
play_source, previous_play_source, previous_play_source_snapshot|
null, context_ref|null, shuffle_seed|null, position_updated_at|
null (ISO 8601, свежесть замера позиции), active_device_id|null
(device_uuid активного устройства), devices[] }, queue: QueueItem[] }`.

`QueueItem`: `{id, player_state_id, added_by_user_id, position,
status: pending|playing_now|played|skipped, snapshot|null}`.

`version` растёт с каждым изменением состояния (команды плеера,
регистрация устройства — состав `devices[]` тоже часть состояния):
устройство применяет апдейт только если `version` новее локального —
отсекает устаревшие/дубли (в дополнение к `command_id`).

| Метод/путь | Тело → Ответ |
|---|---|
| `POST /play` | `{snapshot: {<конверт любого типа>}, playback_source: single\|queue\|favorites\|search\|playlist\|uploads\|wave, origin_device_id, command_id, context_ref?, shuffle_seed?}` → новое состояние; позиция 0, is_playing=true |
| `POST /pause` | `{origin_device_id, command_id, position_seconds?}` — `position_seconds`: точная позиция на момент паузы (её знает паузящее устройство); без поля позиция остаётся последней замеренной, штамп `position_updated_at` не меняется |
| `POST /resume` | `{origin_device_id, command_id}` |
| `POST /seek` | `{position_seconds, origin_device_id, command_id}` |
| `PATCH /options` | `{options: {repeat_mode?, shuffle_enabled?, clips_enabled?}, origin_device_id, command_id, shuffle_seed?}` |

`context_ref` и `shuffle_seed` — непрозрачные строки клиента,
бэк не парсит: поле передали (даже null) — перезаписали, не
передали — не трогаем. `shuffle_seed` доезжает до остальных
устройств и через `PATCH /options` (переключение shuffle без
смены трека).

Жизненный цикл очереди: `POST /play` с `playback_source=queue`
потребляет элемент — ожидающий элемент с тем же снапшотом
становится playing_now, прежний playing_now помечается played
и удаляется.

Все команды возвращают состояние целиком и диспатчат
`playback.state.updated`.

## 6. Очередь (`/player/queue`)

Серверная очередь — приоритетная: фронт врезает её в текущий
контекст (см. frontend.md, «Модель плеера»). Потреблённые
элементы удаляются.

| Метод/путь | Тело → Ответ |
|---|---|
| `GET /` | → очередь целиком |
| `POST /` (60/мин) | snapshot (плоский конверт любого типа) + `origin_device_id?`, `command_id?` → очередь целиком; бродкаст с item `{title, artists}` |
| `DELETE /{queueItem}` | тело `origin_device_id?`, `command_id?` → очередь; бродкаст item=null |
| `PATCH /reorder` (60/мин) | `{item: id, to_index: n (0-based; за пределами — клампится), origin_device_id?, command_id?}` — перенос одного элемента ожидающих на позицию (бэк сдвигает только затронутый диапазон) → очередь; бродкаст item=null. Нет такого элемента — 404 |
| `PATCH /{queueItem}/status` (120/мин) | `{status}` — плеер помечает playing_now/played/skipped; бродкаста нет |

## 7. Аудио-потоки (`/audio`)

| Метод/путь | Тело → Ответ |
|---|---|
| `POST /get-url` | track-снапшот → `{url, ttlSec}` — временная ссылка на поток (Яндекс), ссылку не хранить: запросить заново по снапшоту. Клиент кеширует URL до истечения TTL. |
| `POST /file` | track-снапшот → mp3-файл с `Content-Length` (процент — axios `onDownloadProgress`) и `Content-Disposition: attachment`. Эндпоинт **скачивания для офлайна**, схема единая для источников: `upload` отдаётся с нашего диска (доступ по видимости: 403/404), внешние источники прокси-стримятся чанками с нужными Referer. `Range` прокидывается внешнему источнику (`206` + `Content-Range`, докачка с места обрыва); для `upload` Range игнорируется — файл приходит целиком, докачка рестартом. Отказ источника — `502`. |
| `POST /lyrics` | track-снапшот → `[{text, time_ms|null}]` \| null — строки текста; `time_ms` null — без таймкодов; `text: ""` — разделитель строф (рисуем пустую строку) |

## 8. Видео (`/videos`)

Источники видео: Дзен и YouTube (потоки — relay-ссылки с нашего
хоста, обход блокировок клиенту не нужен). Резолв идёт через
YouTube (Дзен-фолбэк временно отключён в коде), поисковая строка —
«исполнитель — название official»; get-url диспатчит по
`source_type` снапшота.

Режим клипов (глобальный тоггл плеера) — часть состояния плеера:
флаг `clips_enabled` в `state`, переключается через
`PATCH /player/options` и рассылается бродкастом — все устройства
пользователя играют в одном режиме, рассинхрона нет.

| Метод/путь | Тело → Ответ |
|---|---|
| `POST /resolve` (60/мин) | track-снапшот → `{video: VideoSnapshot, streams: [{quality, url}], ttl_sec}` — режим клипов: матчинг «трек → видео» на бэке (YouTube; Дзен временно отключён). Результат кешируется маппингом «трек → видео» в базе: повторные резолвы того же трека идут без поиска источника, потоки всегда свежие. |
| `POST /get-url` (120/мин) | video-снапшот → `{streams, ttl_sec, hls}` — свежие потоки по видео (source-независимый контракт). `hls: null` — HLS-адаптации нет (Дзен всегда, YouTube при деградации ответа). Подробности и схема воспроизведения — ниже. |
| `POST /bind` (60/мин) | `{track: TrackSnapshot, video: VideoSnapshot}` → `{video}` — ручная привязка видео к треку (video — снапшот из резолва/поиска). Перезаписывает глобальный маппинг «трек → видео»: resolve отдаёт привязанное видео всем пользователям; снятия привязки нет — только перемэтч повторным bind. |
| `GET /youtube-cookies` | → `{has_cookies: bool, updated_at: string\|null}` — статус привязки персональных cookies YouTube. |
| `POST /youtube-cookies` (30/мин) | multipart, поле `cookies` (Netscape .txt, «Get cookies.txt LOCALLY» с youtube.com) → 201. Файл хранится зашифрованным и подставляется в YouTube-запросы пользователя (обход «Sign in to confirm you're not a bot»). Добровольно: без него запросы идут без куки (деградация качества/стабильности). Relay-ссылки потоков несут sha256-префикс файла (параметр `ch`) — браузеру заголовок не прикрепить. |
| `DELETE /youtube-cookies` | → 200 — отвязать файл. |

### 8.1. Воспроизведение видео: HLS против прогрессива (инструкция фронту)

Ответ `POST /videos/get-url`:

```json
{
  "streams": [{ "quality": 360, "url": "/yt-resource/video/{id}/stream?itag=18&ch=…" }],
  "ttl_sec": 3600,
  "hls": {
    "manifest_url": "/yt-resource/hls/{id}/manifest.m3u8?ch=…"
  }
}
```

Ссылки относительные (§1.7) — перед подстановкой в плеер
прогнать через `resolveUrl`.

**Правило простое: `hls != null` — играем HLS, `hls == null` — играем
`streams` прогрессивно. Оба поля в одном ответе, переключение —
только через get-url, манифест/потоки сами не рефрешатся.**

**Когда что бывает:**
- Дзен — всегда `hls: null`, только прогрессивные `streams`.
- YouTube — `hls` есть почти всегда: egress residential (без VPN) +
  PO-токены дают полную лесенку качеств (до 2160p). `hls: null` —
  деградированный ответ на конкретном ролике (антибот) — играем
  прогрессив. Это норма, а не ошибка.

**HLS-режим (hls.js, обязателен к клипс-плееру):**
1. Подключить hls.js; источник — `hls.manifest_url` после
   `resolveUrl` (§1.7) — тот же хост, что у API, CORS-заголовки
   не нужны. Манифест уже переписан бэком: вложенные плейлисты
   и сегменты идут через `/yt-resource/hls-seg?u=…` — плеер
   резолвит их от origin манифеста, ничего дальше не трогаем.
2. Качество — авто (ABR) по умолчанию; ручной выбор — стандартный
   API hls.js (`hls.levels` / `hls.currentLevel`).
3. **Аудиодорожки (дубляжи) и субтитры** живут внутри манифеста
   (`EXT-X-MEDIA`) — отдельного поля в ответе нет. Список для UI:
   `hls.audioTracks` / `hls.subtitleTracks`; переключение:
   `hls.audioTrack = i` / `hls.subtitleTrack = i`. Дорожек может
   не быть (ролик без звука) — не показываем селектор, звука не
   будет (mute-состояние, не ошибка).
4. Если hls.js не смог инициализировать (манифест 404/502) —
   фолбэк на прогрессивные `streams`.

**Прогрессив-режим (Дзен и деградация):**
`streams` отсортированы от худшего к лучшему; старт — последний
(максимум) или на выбор юзера; `<video src=url>` напрямую.

**Жизненный цикл (общий для обоих режимов):**
- `cookies_used: true` — этот ответ получен с персональными
  cookies: анонимный запрос уперся в стену, куки ее сняли.
  Бэк тратит куки экономно (аноним-первый, поиск вообще без
  кук — на флагованном IP они живут недолго). Если get-url
  падает 502 у пользователя с привязанными куки — повод
  показать подсказку обновить экспорт.
- Ссылки временные: `ttl_sec` (обычно 3600). До истечения —
  перезапрос `get-url` и подмена источника без остановки
  воспроизведения не требуется, плеер доигрывает старый URL
  (googlevideo держит ~6 ч); после истечения TTL новый запрос.
- Холодный high-itag сегмент первый раз может ждать первого
  байта десятки секунд (origin-pull на edge googlevideo — не
  буферизация нашего стека): таймаут TTFB в hls.js поднимать
  до ~30 с (`fragLoadPolicy.maxTimeToFirstByteMs`). Сегменты
  кешируются микросервисом (диск, TTL 3 ч, LRU): повтор того же
  сегмента — мгновенный (`X-Cache: hit`), обрыв запроса скачку
  не отменяет — ретрай присоединяется к уже идущей (`wait`) и
  получает скачанный префикс сразу.
- Ошибки сегментов/потока (403/410/502 от relay): **один**
  повторный `get-url` → замена источника/манифеста → рестарт
  с последней позиции (`player.seek(...)`). Повторная ошибка —
  честное состояние «видео недоступно», фолбэк на аудио трека.
- `resolve` возвращает `streams` той же формы для немедленного
  старта — реинициализация по `get-url` всё равно нужна по TTL.

## 9. Поиск (`GET /search?q=&limit=&page=`, 30/мин)

`q` (2–100 символов; может быть **ссылкой** на сущность Яндекса —
бэк сам разберёт и вернёт одноэлементную страницу), `limit`
(≤50, размер страницы треков), `page` с 1.

Ответ — страница секциями (все секции всегда на месте):

```json
{ "query": "...", "page": 1, "best": {...}|null,
  "tracks":    { "items": [TrackSnapshot & {is_favorite}], "total": n, "has_more": b },
  "albums":    { "items": [...], "total": n, "has_more": b },
  "artists":   { "items": [...], "total": n, "has_more": b },
  "playlists": { "items": [...], "total": n, "has_more": b },
  "videos":    { "items": [VideoSnapshot & {is_favorite}], "total": n, "has_more": b } }
```

- `is_favorite` — пометка избранного текущего пользователя
  (всегда bool, только в поиске).
- Выдача внешних источников (Яндекс, Дзен, YouTube) кешируется
  на бэке per-user на 10 минут по ключу (источник, строка,
  страница, лимит): повторные поиски, второе устройство и
  догрузка страниц контекстом плеера источники не дёргают.
  `is_favorite` ставится после чтения из кеша — лайки в выдаче
  всегда свежие. Свои источники (загрузки, плейлисты) не
  кешируются: новый контент виден в поиске сразу.
- Порядок в секциях — порядок склейки источников: свои
  (загрузки, плейлисты пользователя) идут первыми, внешние
  результаты — после них.
- Источники могут вернуть перекрывающиеся страницы (у Яндекса
  встречаются дубли на стыке page N / N+1 — особенность его API,
  бэк страницы не дедупит). Клиент при склейке страниц секции
  отбрасывает элементы с уже виденной тройкой
  `(type, source_type, source_id)`.
- `best` — необязательное «лучшее совпадение» в общей
  снапшотной форме + `is_favorite` (как item секций); невалидный
  best от источника отдаётся как null. При поиске по ссылке
  (q = URL) best — разрешённая сущность. У artist в best поле
  `artists` не приходит — как и в секциях.
- Видео-источники (Дзен и YouTube) склеивают секцию `videos`
  вместе (`merge`, `has_more` — OR источников). У Дзена пагинации
  нет (page>1 пусто), у YouTube страницы честные (глубина до
  200 роликов на запрос): листаем `page`, пока секция не придёт
  пустой. Аудио-источники секцию отдают пустой.

## 9.1. Поиск v2 (`GET /search/v2`, 30/мин)

Один источник на запрос, без фан-аута и склейки (v1 `/search`
при этом работает без изменений). Фильтры строгие, `all` нет.

Параметры: `q` (2–500), `resource` (обязателен),
`type` (`audio|video`, шлётся всегда; обязан совпадать
с семейством ресурса — иначе 422), `section` (необязателен;
нарезка ответа до одной секции — из кеша, апстрим не
дёргается), `page` (с 1), `limit` (≤50).

Источники и их секции (значения `resource` = `SnapshotSourceEnum`):

| resource | type | секции | has_more |
|---|---|---|---|
| `yandex_music` | audio | `tracks`, `albums`, `artists`, `playlists` + `best` | честный (Яндекс) |
| `upload` | audio | `tracks` | честный (своя база) |
| `skyfi` | audio | `playlists` | честный (своя база) |
| `dzen` | video | `videos` | advisory: терминатор листания — пустая страница |
| `youtube` | video | `videos` | advisory: потолок глубины 200, терминатор — пустая страница |

Секции «каналы»/«плейлисты из роликов» источники сейчас не
отдают — в контракте зарезервированы, не наполняются.

Ответ — только секции запрошенного источника (с `section` —
ровно одна; `best` отдаётся только у Яндекса и только без
фильтра `section`):

```json
{ "query": "...", "page": 1, "resource": "yandex_music",
  "best": {...}|null,
  "sections": { "tracks": { "items": [...], "total": n, "has_more": b } } }
```

Items — те же снапшоты с `is_favorite`, что в v1. Кеш общий
с v1 (per-user, 10 минут, ключ: источник/строка/страница/лимит):
прогретый v1 источник отвечает v2 без похода в сеть.

### Детали сущностей: `POST /details`

Единая выдача деталей для `type` ∈ `album|artist|playlist`.
Тело — конверт снапшота (`type`, `source_type`, `source_id`;
`title` необязателен — бэк резолвит сущность по паре источника)
+ `page`/`limit` (пагинация треков, как в поиске).

Ответ — `{entity, tracks, albums}`:

- `entity` — снапшот запрошенной сущности (полный: у album

- `albums` — `{items: [AlbumSnapshot], total, has_more}`

## 14. Волна (`/wave`)

Сервер — источник истины ротации: он хранит окно волны, сам
догружает его у источника (Яндекс-ротор) порциями и помечает
прослушанное. Клиент синхронизирует окно целиком: ответ
всегда полное окно, никогда пустой; «окно не выросло» —
догрузки сейчас нет. batch_id и якоря на провод не уходят.

**Прослушанное.** Каждый элемент окна несёт флаг `played`.
Бэк помечает позиционно: на каждый `POST /play` с
`playback_source=wave` всё, что в окне до играющего трека,
становится `played=true` (skip'ы закрываются сами). Отметки
не снимаются: ручной возврат к прослушанному его не
«оживляет». Новый заход в волну стартует с первого
`played=false` — уже прослушанное само не играет, возврат
к нему только ручной.

**Догрузка — по сокету, без запросов «под конец списка».**
Бэк следит за позицией по play-запросам и догружает порцию
сам, когда непрослушанных впереди текущего остаётся мало;
выпрослушанное целиком окно догружается сразу при `GET /wave`.
О выросшем окне клиенты узнают из `playback.wave.updated`
(§17) → делают `GET /wave` и заменяют локальную копию
(текущее воспроизведение при этом не трогают). Отдельный
догружающий запрос от фронта не нужен вообще: `GET /wave`
вызывается на старте волны и по сокет-ивенту.

Только с подключённым Яндексом (иначе 422 + сообщение).
Отключение Яндекса (`DELETE /yandex-music/auth`, §16) чистит
окна волны этого источника.

| Метод/путь | Тело → Ответ |
|---|---|
| `GET /wave` (60/мин) | query `?origin_device_id&command_id` (опционально) → `{snapshots: [(Snapshot & {played: boolean})]}` — полное окно ротации в порядке следования, у элементов флаг прослушанного |
| `POST /wave/feedback` | `{track_id, type: like\|dislike\|skip\|trackStarted\|trackFinished\|radioStarted, total_played_seconds?}` — реакции ротации; batch_id бэк подставляет сам из сохранённого окна |

## 15. Загрузки (`/uploads`)

Свои файлы: `POST /` multipart `{audio (mp3/flac/...), title,
artist_names: [..]}` → upload; `GET /` — список; `PATCH /{id}`
— мета (title, artist_names, album_title, lyrics, visibility);
`DELETE /{id}`; `GET /{id}/stream` — поток файла (постоянная
ссылка, качается и для офлайна).

`lyrics` приходит сырым текстом (форма с textarea) — бэк режет
на строки по переносам (`\r\n`/`\n`), края строк тримит, пустые
строки выкидывает; в снапшоте всегда `lyrics: [{text, time_ms:
null}]` (как у источников), пустой текст → `lyrics: null`.

## 16. Импорт из Яндекса (`/import/yandex-music`)

Без подключённого Яндекса summary/start — 422 «Яндекс Музыка
не подключена.».

- `GET /summary` → `data: {<type>: {total, existing}}` по ключам
  `tracks`/`albums`/`artists`/`playlists`: `total` — сколько
  лайкнуто в Яндексе, `existing` — сколько уже перенесено в SkyFi
  (маркер `import_source: "yandex"`).
- `POST /` (12/мин) → прогресс созданной задачи (старая запись
  пользователя удаляется). Джоба уходит в очередь.
- `GET /` → прогресс активной (или последней) задачи, `data:
  null` — импорт ни разу не запускался. Форма: `{job_id, status,
  total, processed, imported, skipped, failed, progress (0–100,
  completed = 100), message, started_at, finished_at}`.
  `status`: `queued` | `running` | `completed` | `failed` |
  `cancelled`.
- `DELETE /` → отмена: активной/висящей ставит `cancelled`
  (джоба завершит текущую страницу и выйдет), отвечает прогрессом;
  записи нет — `data: null`.

Лайки Яндекса приезжают в избранное с `import_source: "yandex"`.

## 17. Сокеты

**Транспорт**: Laravel Reverb (WebSocket), драйвер в конфиге
бэка. Аутентификация каналов — sanctum (тот же токен,
handshake `POST /broadcasting/auth` — путь на корне origin, вне
префикса `/api/v1/skyfy`; ответ без обёртки, сырой
`{auth: "..."}` от Reverb, не наш `errors/data`). Фронт:
официальный Echo-клиент.

**Каналы** (private):
- `App.Models.User.{id}` — личный канал пользователя (только
  владелец).
- `friends.{id}` — канал пользователя для друзей (подписаться
  может только друг; слушается для now-playing/очереди друга).
- `device.{uuid}` — персональный канал устройства (только
  владелец, `{uuid}` = `device_uuid`). Подписка на него —
  привязка сокета к устройству (presence, см. §4): подписаться
  сразу после коннекта; событий в канал не шлётся, важен сам
  факт подписки/отписки.

**Ивенты** (имена = `broadcastAs`, payload = `broadcastWith`):

| Ивент | Каналы | Payload | Когда |
|---|---|---|---|
| `playback.state.updated` | User.{id}, friends.{id} | `{state, queue, origin_device_id, command_id}` | любая команда плеера, регистрация устройства, стоп при потере активного устройства (presence, см. §4); `state`/`queue` — тот же JSON, что `GET /player` |
| `playback.queue.updated` | User.{id}, friends.{id} | `{item: {title, artists}\|null, origin_device_id, command_id}` | add (item заполнен — тост «добавлено»), remove/reorder (null) |
| `playback.wave.updated` | User.{id} | `{origin_device_id, command_id}` | окно волны выросло (холодный старт, догрузка): клиент делает `GET /wave` и заменяет локальную копию, воспроизведение не трогает. Эхо-поля информационные: глушение эха на этот ивент не распространяется — при догрузке от play-хука оба null, и инициатор play тоже обновляет копию |
| `friend.queue.item.added` | User.{id} очередника | `{added_by: {id, name}, item: {source_id, title, artists}}` | друг добавил в мою очередь |
| `playback.device.connected` | User.{id} | `{device, origin_device_id}` | регистрация устройства; переход устройства в онлайн по сокету (presence) |
| `playback.device.changed` | User.{id} | `{device_uuid, origin_device_id}` | смена активного устройства |
| `playback.device.disconnected` | User.{id} | `{device_uuid, device_name, origin_device_id, command_id}` | удаление устройства; устройство офлайн по сокету (разрыв + грейс 60 с) |
| `friendship.request.sent` | получатель | дружба целиком `{id, sender{...}, receiver{...}, status}` | заявка |
| `friendship.request.accepted` | отправитель | то же | принята |
| `share.sent` | получатель | `{share_id, sender: {id, name}, snapshot}` | шара |

**Семантика эхо**: устройство-инициатор сравнивает
`origin_device_id` со своим `device_uuid` — совпало,
значит эта команда его же: применять локально повторно не надо
(он уже применил оптимистично). `command_id` — дополнительная
дедупликация. Playback-ивенты на канале `friends.{id}` —
для экранов друга; эхо-поля там игнорируются. Исключение —
`playback.wave.updated`: эхо-глушение на него не действует,
окно обновляют все устройства, включая инициатора команды.

**Reconnect**: при восстановлении соединения фронт делает
`GET /player` и подменяет локальное состояние серверным
(сервер — источник истины), сокет-дельты дальше накатываются
по `version`.

## 18. Коды ошибок, которые фронт обрабатывает явно

- 401 → на выход из сессии (на ТВ — на экран QR).
- 422 → показ полей из `errors`.
- 429 → тост «слишком часто».
- 404/403 с сообщением в `errors` → тост сообщением.
- 502/503 → тост «внешний сервис недоступен» (Яндекс
  не отвечает / не подключён).

## 19. Обновления приложения (`/app-updates`)

Один механизм обновляет и нативную оболочку (APK Capacitor), и
веб-часть: клиент спрашивает `GET /app-updates/check`, бэк отвечает
оффером с полем `kind` — `apk` (новая оболочка) или `bundle`
(OTA ZIP-бандл веб-части, Capacitor live updates — применяется без
переустановки). Оффер оболочки приоритетнее: свежий APK несёт
актуальный бандл внутри, а после установки следующий check
предложит бандл, если тот ещё новее. Нативные изменения (новые
плагины, пермишены) — по-прежнему новым APK, для этого у релиза
бандла есть `shell_min_version`.

| Метод/путь | Тело → Ответ |
|---|---|
| `GET /app-updates/check` (30/мин, auth) | query `?platform=android&current=<версия бандла>&shell=<версия оболочки>[&apk=1]` → `data: {kind, version, url, sha256, size_bytes, mandatory, notes}` или `data: null` (обновления нет: клиент актуален либо оболочка несовместима) |
| `GET /app-updates/download/{id}` | подписанная ссылка из `url` бандла (без токена, живёт 60 мин) → ZIP-файл (`application/zip`) |
| `GET /app-updates/download-apk/{id}` | подписанная ссылка из `url` оболочки (без токена, живёт 60 мин) → APK: `application/vnd.android.package-archive`, attachment `SkyFi-<version>.apk` |

- `kind`: `bundle` \| `apk`. Параметр `apk=1` — клиент умеет
  принимать офферы оболочки; без него `kind: apk` не выдаётся
  никогда (старый клиент попытался бы поставить APK как ZIP-бандл),
  со старым клиентом новый бэк работает как раньше. Ответ без
  `kind` (ещё более старый бэк) клиент считает бандлом.
- Правило выдачи при `apk=1`: есть релиз оболочки с `version` >
  `shell` запроса (semver, `version_compare`) — оффер оболочки,
  даже если есть и более новый бандл; иначе — существующая логика
  бандла (включая фильтр `shell_min_version`).
- Версии — semver `X.Y.Z`, сравнение на бэке `version_compare`.
- `url` строится от адреса запроса (как все ссылки) — работает
  и по LAN, и по внешнему адресу.
- `mandatory: true` — обновление обязательное: у бандла клиент
  блокирует работу до установки; у оболочки — диалог без «Позже»
  (факт установки клиент не проверяет: оболочка осталась старой —
  оффер повторится при следующей проверке).
- Публикация бандла (на бэке): собрать фронт (`npm run build`),
  заархивировать `dist` в ZIP и выполнить
  `php artisan app:release dist.zip 1.4.0 --shell-min=1.0.0 [--mandatory] [--notes="Что нового"]`.
  Повтор той же версии — 409.
- Публикация оболочки (на бэке):
  `php artisan app:release-apk <path-to.apk> 1.1.0 [--mandatory] [--notes="…"]`
  (копия файла в `storage/app/app-shell-releases`, sha256, запись
  в БД). Повтор той же версии — 409. Полный цикл сборки и
  публикации — `scripts/release-apk.sh --shell=X.Y.Z [--mandatory] [--no-publish]`.
- Клиент с `kind: apk` открывает `url` вне WebView: ссылку
  забирает системный браузер, APK качает он, установку подтверждает
  штатный установщик Android (подпись пакета сверяет сам Android,
  обновление встаёт поверх при совпадении подписи).

**Интеграция на фронте** (плагин `@capgo/capacitor-updater`,
self-hosted/manual режим — без Capgo-сервера):

1. Версию бандла держать в коде (константа, совпадает с тегом
   релиза), версию оболочки — из нативного слоя (например,
   `App.getInfo().build` или константа, поднимаемая при сборке
   APK).
2. При старте приложения (и по pull-to-refresh/кнопке
   «Проверить обновления»): `GET /app-updates/check`. `null` —
   ничего не делаем.
3. Есть обновление → фоном `CapacitorUpdater.download({url,
   version, checksum: sha256})` — плагин сам скачает и сверит
   хеш. Прогресс — по `size_bytes`.
4. Скачано → диалог «Обновить до {version}? {notes}» → по кнопке
   `CapacitorUpdater.set(bundle)` — применение без переустановки.
   `mandatory` — диалог без отмены.
5. После успешного старта нового бандла обязательно
   `CapacitorUpdater.notifyAppReady()` — иначе плагин откатит
   на предыдущую версию (встроенная защита от битых бандлов).
6. `shell < shell_min_version` бэк отфильтрует сам — клиенту
   достаточно честно слать свою версию оболочки.
