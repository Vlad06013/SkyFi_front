# SkyFi Frontend — требования и модели

Требования к фронтенду: архитектура, страницы, плеер, офлайн,
скачивание, предзагрузка, железо. Контракт бэка — в `api.md`,
этот документ на него ссылается и не дублирует поля.

- Стек: **Vue 3 + Ionic + Capacitor** (билд APK сохранён).
- Цели: один APK (телефон, Android TV, автомагнитола Teyes
  cc3) + браузер. Десктоп (Win/Ubuntu) — опционально позже
  (обёртка поверх веб-сборки, стек позволяет; не блокер).
- Старт: с нуля. Старый фронт (`SkyFi_front`) — только
  справочник в папке `_old`; логику плеера и списки оттуда
  переносим по результатам отдельного исследования (шаг 2).

## 1. Адаптивные профили (один APK)

Один визуал на `phone` / `tv` / `car` / `computer`. Экраны
из кита телефона, ширина меняет масштаб. Тип устройства
регистрируется на бэке; в браузере — по размеру/user-agent.

- **TV**: те же экраны, D-pad даёт видимый фокус; медиа-пульт
  — play/pause/next/prev/seek. Вход — QR (нет клавиатуры).
- **Магнитола (car)**: те же экраны, ландшафт и кнопки руля.
  Вход — QR.
- **Phone**: тач. Может показать QR и подтвердить чужой вход.

## 2. Архитектура кода и конвенции файлов

Цель: человекопонятный код, никаких гигантских нечитаемых
файлов. Каждая единица маленькая и отвечает за одно.

### 2.1. Структура компонента и страницы

Каждый компонент и каждая страница — папка с тремя файлами
одним именем:

```
PlayerControls/
├── PlayerControls.vue   — только <template>
├── PlayerControls.ts    — defineComponent: setup, состояние, методы
└── PlayerControls.css   — стили (scoped)
```

- `X.vue` — вёрстка одним файлом. Подключает скрипт и стили
  соседними файлами: `<script src="./X.ts" lang="ts"></script>`
  и `<style scoped src="./X.css"></style>`. Из шаблона
  доступно всё, что `setup()` вернул в `return`, плюс пропсы
  и зарегистрированные в `components:` компоненты. (Вариант
  `<script setup src>` не используем: vue-tsc не подхватывает
  внешний setup-файл для типизации шаблона.)
- `X.ts` — вся логика: `export default defineComponent({...})`
  с опциями `name` (многословное), `components`, `props`,
  `emits` и `setup()`. В `setup()` объявляем refs/computed/
  handlers; в конце явный `return {...}` всего, что
  использует шаблон. Никаких шаблонов в строках, никакого
  HTML из скрипта.
- `X.css` — только стили этого компонента (scoped). Тема,
  токены и глобальные стили — в отдельном `styles/` (тоже
  расколотом на файлы: tokens.css, base.css, ...).

Лимиты: ts-файл перевалил за ~250 строк — логика уходит в
composables (`useX.ts`) рядом; template распух — подблоки
выносятся в дочерние компоненты (по этой же схеме).

### 2.2. Слои и направление зависимостей

- `api/` — клиент бэка по главам api.md: `api/player.ts`,
  `api/queue.ts`, `api/search.ts`, ... Только HTTP и типы
  запросов, никакой логики UI.
- `types/` — TS-модели снапшотов и enum-значения (зеркало
  api.md §2, готовая копия — contracts.md). Единственное место, где живут строковые
  литералы типов и источников.
- `stores/` — Pinia: player, queue, library, offline,
  devices. Состояние и действия, без обращений к DOM.
- `composables/` — переиспользуемая логика (usePlaybackScheme,
  useEchoSuppress, useDownloads, ...). Скрипты-компаньоны
  компонентов держатся маленькими за счёт composables.
- `components/` — UI-блоки по правилам §2.1, бизнес-логика
  только через composables/stores.
- `pages/` — экраны из карты (§4), состоят из компонентов.

Правило: `pages → components/composables → stores → api`.
Обратных ссылок нет (api не знает про stores, stores не
знают про компоненты).

### 2.3. Общие требования

- Читаемость важнее краткости: явные имена
  (`activeDeviceId`, а не `ad`), без магических чисел и строк
  вне types/.
- Комментарии — только «почему», не «что».
- ESLint + Prettier в CI-стиле: форматирование не обсуждается,
  руки не болят.
- Никаких гигантских файлов: видим файл на 400+ строк —
  режем по §2.1–2.2.
- Не дублируем разметку: повторяющийся UI-блок (шит, строка,
  меню, хэндл) выносим в компонент и переиспользуем; встретил
  третью копию — сначала компонент. Общий шит — `AppSheet`
  (`src/components/AppSheet/`): маска, Esc, хэндл со свайпом
  вниз, заголовок.
- Страницы вкладок под `TabsLayout` обёрнуты в `keep-alive`
  (`router-view v-slot`): «назад» из деталки возвращает на тот
  же экран с состоянием (поиск с запросом и выдачей, таб
  медиатеки), а не на пересозданный. Данные по-прежнему тянем
  стор-вачерами, не `onMounted`-ами: кэш не должен заменять
  свежесть. Прокрутка общая (`.sky-body`): уход со вкладки
  запоминает `scrollTop`, вход возвращает свой. Главная всегда
  с нуля — её экран не скроллится, и сдвиг «Моего» её не уносит.

## 3. NFR железа

- **MediaSession API** (Android): кнопки руля, гарнитуры,
  BT-профилей — play/pause/next/prev; метаданные и обложка
  текущего трека на экране блокировки и в BT-панели авто.
- Пульт ТВ: media-кнопки → плеер; D-pad → фокус по
  элементам страницы (Ionic focus management).
- Фоновое воспроизведение: foreground service (Capacitor
  плагин аудио), уведомление плеера с next/prev.
- Аудиофокус: пауза при звонке/навигации, ducking по системе.

## 4. Карта страниц

Вкладки нижней навигации: **Главная · Поиск · Медиатека ·
Друзья · Настройки**.

1. **Главная (плеер-центричная)** — не «раздел волна», а плеер
   с режимами. Слои: мини-плеер (глобальный) и развёрнутый
   плеер (now-playing: обложка, тексты `/audio/lyrics`,
   очередь, repeat/shuffle, выбор устройства, видео-режим).
   Режимы главной: волна (см. §6), локальный радио-режим.
2. **Поиск** — строка, история (локально), выдача 5 секциями
   (api.md §9), вставка ссылки → одноэлементная выдача.
   Следующая страница секции запрашивается, пока ответ не
   пустой: `has_more` всегда `false`, на него не смотрим.
   Офлайн — поиск по скачанному. При скачивании в базу пишется
   строка: у трека исполнители, название и альбом; у альбома и
   плейлиста то же плюс строки их треков. Ищем по ней. В выдаче
   скачанные треки и целиком скачанные альбомы и плейлисты.
   Артистов и видео в офлайне нет. В строках треков
   и видео (здесь и в медиатеке, включая загрузки и скачанное)
   слева от «⋯» длительность: `m:ss`, от часа — `h:mm:ss`
   (`1:27:20`). Нет `duration_ms` — ничего не пишем.
3. **Детали сущности** — альбом/исполнитель/плейлист
   (`/details`): карточка + содержимое + кнопка «играть
   контекстом».
4. **Медиатека** — вкладки: Избранное (4 секции; впоследствии
   +видео), Плейлисты (свои + материализованные внешние),
   Загрузки (список + загрузка файла).
5. **Плейлист (свой)** — создать: имя и видимость
   (`POST /playlists`); состав, add/remove/reorder, обложка,
   видимость; внешний плейлист — только просмотр/играть,
   пока не в избранном; лайк даёт правку (материализация —
   api.md §11).
6. **Друзья** — список, заявки (incoming/outgoing), поиск
   пользователей; страница друга: now-playing, избранное,
   очередь друга; действия: заявка/принять, «в очередь»,
   «поделиться».
7. **Входящие** — шары «поделились со мной» (принять в
   плейлист/избранное — клиентскими действиями).
8. **Устройства** — список онлайн-устройств, выбор активного
   (пульт), presence-статусы. Вход на ТВ/магнитоле — через
   **QR-экран** (api.md §3).
9. **Настройки** — профиль/аватар, подключение Яндекса
   (device-auth флоу + статус), загрузка cookies YouTube
   (карточка под Яндексом: статус, файл .txt, сворачиваемая
   подсказка с предупреждением «не свой аккаунт»), скачивание
   APK (`raw` файла `skyFy.apk` из ветки `dev_v2`; Linux и Windows
   и пункт «Обновить» пока скрыты), импорт
   (прогресс), офлайн менеджер (скачанное, очередь закачки,
   занятое место), выход.
10. **Авторизация** — логин/восстановление; на ТВ — QR-экран.

Плеер, видео-режим и очередь — **не** отдельные страницы,
а слои/панели поверх (глобальный мини-плеер + развёрнутый).

## 5. Модель плеера (ядро)

**Контекст** — список, из которого запущен трек. Значения
`playback_source` (api.md §5): `single`, `favorites`, `search`,
`playlist`, `uploads`, `wave` (+ `queue` как слой).
Фронт хранит текущий контекст (элементы + позицию курсора) и
строит из него схему воспроизведения.

Синхронизация контекста между устройствами — указатель, не
содержимое: `play_source` + `context_ref` в серверном стейте,
каждое устройство материализует список сам (`lib/context-resolver.ts`):
favorites/uploads/волна — одним запросом, search — по query
(ref — сам запрос, секция по типу текущего снапшота),
playlist — по составному ref `source_type:source_id` через
`POST /details` (постранично; движок догружает страницу, когда
next упирается в край загруженного). Переходы движка и next
пульта `context_ref` серверный не стирают (пульт = зеркало);
очередь ref не трогает — в ней живёт прежний контекст возврата.

**Виртуальный поток** = история + текущий + серверная очередь
(врезана после текущего) + остаток контекста. Очередь
приоритетнее: следующим играет `pending` элемент очереди; её
порядок фиксирован сервером и ручной сортировкой, shuffle её
не трогает (очередь = «друг за другом»). Очередь кончилась —
продолжаем контекст с точки возврата (бэк хранит
`previous_play_source_snapshot` — сценарий живёт через
перезагрузку и смену устройства). Единственное исключение —
repeat=one на автопереходе (см. Next).

**Next**:
1. Ручной next: есть очередь → первый `pending` (repeat=one
   игнорируется — кнопка «дальше» всегда идёт в очередь).
2. Автопереход (трек доиграл): `repeat=one` → повтор текущего,
   **очередь не перебивает повтор** (отраслевой дефолт
   Spotify/Яндекс Музыка: трек крутится, пока повтор не
   выключат или не нажмут next); иначе есть очередь → первый
   `pending`.
3. Очередь кончилась/пуста — следующий элемент контекста с
   учётом shuffle.
4. Конец контекста: `all` — цикл по контексту (по
   перемешанной копии при shuffle); `off` — **переход в
   избранное с начала** (новый контекст FAVORITES). Плеер
   никогда не остаётся пустым (режим бесконечной игры).

**Prev**: в рамках виртуального потока (очередь включена);
если трек уже ушёл дальше 3 с — рестарт текущего в 0 (сразу
в элемент, даже когда серверная позиция ещё не сдвинулась),
иначе предыдущий. Дальше назад некуда (начало контекста,
передний край окна волны, single) → рестарт **всегда,
независимо от repeat** (решено 2026-11-23) — глобальное
правило всей логики плеера, не только волны.

**Shuffle**: порядок — детерминированная перестановка контекста
(hash-сортировка элементов по `shuffle_seed` из стейта,
§plan-player.md); переключение не рвёт текущий трек; repeat all
циклится по перемешанной копии. **Очередь не перемешивается** —
shuffle перемешивает только сегмент контекста. Ролл ключа: на
каждом пользовательском play и на включении shuffle
(выкл→вкл = «перемешать заново»); движок ключ не трогает.

**Single** (`playback_source=single`): контекст из одного трека;
при next — избранное с начала.

**Кросс-девайс (пульт)**: активное устройство (`active_device_id`)
играет и является **источником истины о воспроизведении**
(текущий снапшот, позиция, is_playing — его локальные, серверу
оно репортит); серверный стейт нужен для синхронизации
устройств, а не для управления активным. С любого другого
устройства пользователь шлёт команды (play/pause/next/seek/
options) — бэк вещает на все; инициатор глушит эхо по
`origin_device_id`. Смена активного устройства —
`PATCH /devices/{id}/activate` (живёт в player store: ответ —
полный стейт, применяем сразу), после неё поток продолжается
на новом устройстве с того же состояния; бывшее активное глушит
аудио и становится пультом. **Видео (клипы и чистые видео)
показывают все устройства** — пульт в mute (`clips_enabled`
серверный, а картинка — локальная подмена потока на каждом
экране: резолв `/videos/resolve` каждое устройство делает себе
само), звук и переходы двигает только активное. Presence: неактивные устройства
исчезают из списка по таймауту heartbeat, **но бэк об этом не
вещает** — активное могло умереть молча. Поэтому команды
«играй здесь» (`/play`, resume) с устройства, которое не
активно, начинаются со свежего `GET /player`: онлайн-активного
нет (`active_device_id` null или его нет в `state.devices`) —
устройство **активирует себя само** и только потом шлёт команду;
онлайн-активное есть — остаёмся пультом, чужую активацию не
перехватываем (решено 2026-11-25). Пауза/seek/options активацию
не вызывают никогда.

**Применение состояния** — по ролям (решено 2026-11-23):
- Пульт: зеркало серверного стейта, обновляется только из
  источников по приоритету: ответ команды → сокет-ивент
  (если `version` новее локального) → `GET /player` на
  reconnect (полная подмена зеркала). Позиция между апдейтами
  экстраполируется от серверного замера `position_updated_at`
  (докид `now − штамп`, доверие с клампом 30 с — страховка от
  протухшего штампа и кривых часов): позиционные репорты
  активного не дёргают слайдер рывком (2026-11-25).
- Активное устройство: состояние воспроизведения — своё; из
  сервера применяет ровно три вещи: чужую команду
  (`origin_device_id` ≠ мой) — выполняет как команду движку;
  смену `active_device_id` — глушение аудио, становимся
  пультом; reconnect — **слияние по владению**, не подмена:
  поля координации сервера (`active_device_id`, очередь,
  `play_source`/`context_ref`, `shuffle_seed`, presence,
  version) берутся из сервера, факт воспроизведения остаётся
  локальным, если активное устройство всё ещё мы. Слияние —
  только когда серверный стейт уже применялся в этой сессии;
  холодный старт — всегда полная подмена (2026-11-25).
- Конфликтов «два пульта» не избегаем: последняя команда
  побеждает.

**Иконка плея — от факта, не от сервера**: активное устройство
показывает воспроизведение по событию `playing` элемента
(`audioPlaying`), а не по `is_playing` сервера. Рассинхрон дольше
1.5 с (автоплей отклонён при загрузке, протухший поток) — иконка
честно становится «пауза» (`isPlaying` в сторе, грейс нужен,
чтобы не мелькало на переходах между треками). Пульт и гости
зеркалят сервер — им верить нечему.

**Реконсиляция рассинхрона** (код на месте, вызовы закомментированы):
свежая страница сама не играет (автоплей без жеста отклонён — в
WebView APK всегда), поэтому при первом применении серверного стейта
активное устройство сразу слало **реальную паузу** с позицией
(`reconcileBoot`, одноразово) — сервер и пульты знают правду, значок
падает в паузу из ответа, без окна притворства. Дальше застрявший
рассинхрон (протухший поток посреди сессии) добирала обычная
реконсиляция: молчание дольше 3 с при не грузящемся потоке
(`engineLoading` репортят движки) — та же реальная пауза. Пока поток
грузится или буферизуется — не шлём. Отдельно `streamWarming`:
источник уже применён, но элемент ещё не прислал `playing`. `canplay`
прогрев не снимает — у холодного HLS он приходит на крошечный буфер,
пока сегмент с origin ещё едет, и пауза обрывала старт (дальше resume
тут же добивался новой паузой). Сейчас оба вызова (`reconcileBoot` и
`pauseToServer` из тика) не стартуют: пауза на бэк из рассинхрона не
уходит.
Тап по play до сети зовёт `unlockMediaPlayback`: немой play() внутри
жеста снимает запрет автоплея, и `play()` после get-url уже со звуком.
Первый тап до реконсиляции пинает элемент напрямую (`engineKick` →
`el.play()`, при `el.error` — перезагрузка потока) — жест
пользователя проходит автоплей, пауза на бэк не уходит. Resume
после протухшего потока тоже перезагружает поток, иначе цикл
«resume → молчание → авто-пауза».

**Стартовая позиция трека** (`resumeAt`): захватывается на старте
загрузки потока, а не по окончании fetch — иначе таймапдейты ещё
играющего старого элемента пересаживают якорь стора, и новый трек
стартовал бы с позиции старого. Гейты на якорь/timeupdate/дрейф
смотрят `appliedKey` (что реально в элементе), а не `loadedKey`
(что собирались загрузить).

Новое видео (не TTL и не смена качества) стартует с серверной
позиции, обычно 0. `currentTime` того же `<video>` — это ещё
предыдущий ролик; hls.js на `startLoad(-1)` подставляет его как
`lastCurrentTime`. Поэтому в `hlsLoad` уходит явный `startLoad`,
а `timeupdate` не якорит стор, пока элемент не окажется рядом с
целевой позицией — иначе пинг увозит старые секунды seek'ом.

**Тап по строке списка — тоггл** (`playOrToggle`, единый вход
`openSnapshot` и строк всех списков): тап по текущему снапшоту
(совпадение по snapshotKey) — пауза/плей, по иному — прямой
запуск. Явные CTA «играть всё» и пункт меню «слушать» — всегда
прямой запуск.

## 6. Волна (режим главной)

Три состояния:
1. **Яндекс подключён + онлайн** — реальная волна: окно
   ротации живёт на бэке (api.md §14), клиент синхронизирует
   его целиком: `GET /wave` → полная замена локальной копии;
   `playback.wave.updated` → рефетч + замена целиком, без
   диффинга. Волна единая на аккаунт. Контекст плеера =
   `wave`. Feedback Яндексу — позже (отдельное обсуждение).
   Пульт волны: текущий трек + управление, без превью и
   next (MVP, см. plan-player.md).
2. **Онлайн, Яндекс не подключён** — тот же экран с CTA
   «подключить Яндекс» (device-auth флоу из api.md §3).
3. **Офлайн** — тот же экран волны играет по локальному
   контенту (скачанное + кеш избранного), имитация радио
   (как было в старом фронте).

Предзагрузка волны — как у треков (§9): держать 3 следующих
(батч + следующий батч по якорю).

## 7. Видео-режим (клипы)

Глобальный тоггл плеера «видео» — серверный флаг `clips_enabled`
(api.md §5, `PATCH /options`): устройства играют в одном режиме,
рассинхрона «на одном видео, на другом аудио» нет. Локальный
`clipMode` стора — зеркало флага: применённый серверный стейт
(ответ команды, сокет, reconnect) его выставляет; тогл —
оптимистичная команда с откатом. Мок-режим (гость) тоглит
локально. При включении для текущего трека
`POST /videos/resolve` → `{video, streams, ttl_sec}` →
свой `<video>`/ExoPlayer со списком качеств (дефолт 720,
селектор). `video=null`/ошибка → остаться на аудио, показать
индикатор «клип не найден». Ссылки протухают (TTL) — перед
стартом/по истечении запрашивать `videos/get-url` заново.
Кнопка «открыть оригинал» — `watch_url`. В поиске видео
приходит секцией `videos` (мок) — при клике играется как
видео напрямую (snapshot уже video-типа, resolve не нужен —
сразу `videos/get-url`). Чистое видео в `current_snapshot`
играет как видео независимо от флага: UI смотрит
`clipActive` (эффективный снапшот — видео), а не `clipMode`.

**HLS и аудиодорожки (api.md §8.1).** Полный ответ несёт только
`get-url`: `{streams, ttl_sec, hls: {manifest_url} | null,
cookies_used}` (форма проверена curl'ом). В `resolve` ни `hls`,
ни `cookies_used` нет — его `streams` для немедленного старта,
а полный ответ добираем get-url'ом сразу после старта (движок
подменяет источник на манифест с уже назначенной позиции,
не с `currentTime`: до seek он ещё 0 и клип начинался сначала). `hls != null` —
манифест играем через hls.js (ленивый импорт, `lib/hls-engine.ts`,
элемент тот же singleton): качество — ABR с потолком `clipQuality`
(`autoLevelCapping`), ручной выбор фиксирует уровень
(`currentLevel`), пункт «Авто» возвращает ABR; высоты пунктов
селекта приходят из манифеста (`MANIFEST_PARSED`, уровни уже
отсортированы по высоте). Выбор качества по прогрессив-списку
`streams` не клампим, пока жив HLS (у YouTube там один 360p —
список не описывает лесенку): кламп `clipQuality` по потокам —
только в прогрессив-режиме (`clampClipQualityToStreams` после
get-url без `hls`), в HLS — по высотам манифеста. Конфиг hls.js:
`maxBufferLength: 30, maxMaxBufferLength: 60` — дефолтный
`maxBufferSize` (60 МБ) раздувает цель форвард-буфера до 600 с
на низкобитрейтных ступенях, и клип скачивался целиком одним
залпом (сотня запросов на ролик). Повторное применение того же
качества к живой сессии пропускаем (`appliedQualityKey`): любой
`currentLevel` — это flush+перезагрузка буфера, и фоновые reapply
(TTL, ретрай get-url) иначе роняли воспроизведение, а в auto
сбрасывали подъём ABR; смена только потолка в auto — без сброса
буфера. Фатальная сетевая ошибка останавливает загрузку hls.js —
после ретрая get-url с тем же манифестом будим её `startLoad()`
(`hlsResume`). `hls == null` —
прогрессив, как раньше (Дзен всегда; YouTube при деградации —
норма, не ошибка).
Аудиодорожки (дубляжи) и субтитры живут внутри манифеста
(`EXT-X-MEDIA`), отдельного поля нет: список — `hls.audioTracks`,
переключение — `hls.audioTrack = id`. Селектор — чипом рядом с
качеством; выбор храним id дорожки (LANG у YouTube-манифестов
нет), одинаковые «Default»-дорожки разных групп склеиваем в один
пункт, метчинг id → default. Селектор показываем при >1 дорожке;
пустой список — ролик без звука: mute-состояние, не ошибка.
Субтитры отдельным UI не выносим (в манифестах YouTube их нет).
`cookies_used: true` — ответ получен с персональными cookies,
информационный флаг; если get-url/resolve падает 502 у пользователя
с привязанными cookies (статус — `stores/youtube`) — тост
«обновите экспорт» (Настройки → YouTube), один раз на видео,
воспроизведение не прерываем. Ошибка потока/сегмента (progressive
`error` + фатальный ERROR hls.js) — один повторный get-url с
подменой источника/манифеста и рестартом с позиции (resumeAt на
`loadedmetadata` работает и с MSE); повторная — HLS сдаётся в
пользу прогрессивных `streams` (манифест для этого видео больше
не поднимаем), повторная уже на прогрессиве — честное «клип
недоступно», фолбэк на аудио трека. Нет MSE (старый WebView) —
сразу тот же фолбэк на прогрессив.

Клип — **подмена снапшота**, а не второй поток поверх трека:
пока клип активен, для движков и прогресса «текущий снапшот»
— это видео (`effectiveCurrent` в сторе плеера): аудио-движок
замолкает и сбрасывает свой поток, ползунок живёт по
длительности клипа. Очередь, волна и движок переходов по-прежнему
работают с треком — `ended` видео ведёт себя как конец трека.
**Позиция одна на оба снапшота**: при тоггле она переносится
как есть, секунда N на клипе ≠ секунде N трека — осознанный
компромисс MVP. Тоггл обратно — возврат к треку с той же
позиции (поток аудио перезапрашивается и встаёт на неё).

Сворачивание плеера клип не останавливает: картинка переезжает
в мини-плеер, на главной — в диск. У аудио диск квадратный, кнопки
под ним. У видео диск на всю сцену (вне потока, с тем же отступом),
«В волну», прогресс и кнопки лежат поверх, аура остаётся по краям.
Хост снимается до уничтожения
узла: элемент без документа браузер ставит на паузу, поэтому пока
видимого хоста нет, он ждёт в скрытой парковке, а не «без родителя».
Тап по нижнему плееру только разворачивает его: в видео тот же
клик не ставит паузу и не запускает (кнопка play отдельно).
Клик открытия не доходит до развёрнутого слоя. Кнопки при открытии
всегда поверх превью и спиннера и не уходят в простой, пока спиннер
крутится или стоит пауза. Тап по клипу —
пауза/плей через команду стора, но только когда хром уже виден.
Клики по кнопкам управления не всплывают на этот тап. Повторный
toggle в те же 400 мс игнорируется: смена иконки паузы под курсором
иначе проваливала клик на экран и сразу слала resume.
В простое первый клик и движение мыши лишь поднимают плеер, иначе
тот же клик ставил бы паузу. Двойной тап — полный экран (`requestFullscreen`
на элементе, contain вместо обложечного cover). В развёрнутом
плеере обработчики висят на корне: до самого `<video>` тап не
доходит (слоёный UI и `preventDefault` драга гасили бы click),
а в простое клики идут через `pointer-events:none` слоя — в обоих
случаях событие всплывает сюда; драг сворачивания в клип-режиме
не стартует, свайп доступен с хрома экрана.

**Индикация буфера.** Сикбар развёрнутого плеера показывает
буферизованные диапазоны активного элемента (клип — video, трек —
audio) полупрозрачной заливкой под полосой прогресса: опрос
`el.buffered` раз в 500 мс (события `buffered` не покрывают
flush), сброс буфера (flush при смене качества) виден сразу.
Спиннер по центру видео — пока ролик открывается и по `waiting`,
если воспроизведение включено. На паузе его нет: после обновления
страницы буфер часто уже есть, а `playing` не приходит (автоплей
запрещён) — крутить в этом случае нечего. У трека тот же спиннер на обложке — в мини-плеере, на большой
обложке развёрнутого и на диске главной — пока качается ссылка
или поток (`engineLoading` / `streamWarming`) и сервер считает,
что играем. На диске главной при клипе крутится `clipBuffering`.
Обложка (`cover_url` видео-снапшота: у чистого видео — сам
`current`, у трека в режиме клипов — резолвнутый клип; в
развёрнутом — `.clip-bg`, в мини — `.mp-cover`, на главной —
диск) стоит, пока нет кадра на целевой позиции. Пока резолв
ещё не приехал, на месте превью остаётся обложка трека. Как только элемент на паузе
имеет данные и `currentTime` совпал с позицией — показываем этот кадр,
а не превью из поиска. Во время play обложку сменяет первый
представленный кадр (`is-ready`).

**Рассинхрон с сервером**: сервер уверен, что играем, а элемент
активного устройства молчит (после загрузки страницы с
отклонённым автоплеем, протухший поток). Тап в этом состоянии
пинает движок напрямую (`engineKick` → `el.play()`; у аудио при
`el.error` — перезагрузка потока), иконка плея падает в честную
«паузу» через грейс, а застрявший рассинхрон уходит реальной
паузой на сервер (см. §5 «Реконсиляция»).

## 8. Офлайн

**Детект**: периодический `GET /health` (без авторизации) +
состояние сокета. Три состояния: онлайн / нет сети / бэк
недоступен. Вход в приложение офлайн невозможен (нужна
сессия); офлайн доступен, если сессия была.

**Что доступно офлайн**: главная/плеер, медиатека (кеш),
поиск по скачанному (трек, исполнитель, альбом, плейлист). Не доступно:
вход, волна Яндекса (→ локальный режим), друзья, шары,
импорт, активность устройств.

**Избранное — два режима одного списка**: онлайн играет все
элементы; офлайн — только скачанные. Нескачанные треки,
загрузки, альбомы и плейлисты видны, но бледные: не открываются
и без контекстного меню. Артисты и видео скачать нельзя —
они бледные всегда. «Скачать всё» на треках, альбомах и
плейлистах в офлайне не нажимается. Конец любого контекста
офлайн → избранное (скачанное) с начала.

Вход в офлайн (в том числе первая проверка) показывает тост
«Офлайн-режим» на любом экране. Возврат онлайн — тост
«Соединение восстановлено». На главной остаётся плашка
«Офлайн-режим» без подписи «играет скачанное».

«Очистить скачанное» в настройках удаляет файлы, связи и
обложки после подтверждения.

**Очередь мутаций**: лайк/дизлайк/порядок избранного офлайн
применяются к локальному кешу и складываются в очередь
`{action, snapshot triple, sort?, timestamp}`; при онлайне —
отправляются на бэк (лайк/дизлайк — POST/DELETE favorites,
сорт — при выходе из режима редактирования). Конфликты
решает сервер (последняя запись побеждает); после синка —
рефетч избранного.

**Очередь плеера офлайн**: локальный контекст работает;
серверная очередь недостижима — добавления кладутся в локальную
очередь и **не** синхронизируются (MVP); при онлайне —
`GET /player` подменяет локальное состояние серверным
(сервер — источник истины).

Стейт плеера, очередь и материализованный контекст пишутся в
IndexedDB при каждом обновлении и поднимаются до ответа
`GET /player`. Если сети нет, остаётся последняя копия.
Команды `play` / `pause` / `resume` / `seek` в офлайне не
отправляются: это устройство играет скачанный файл само,
тост про регистрацию устройства не показывается.
Шаффл офлайна идёт по скачанным трекам текущего списка.
Когда цепочка доиграна, следующий трек берётся из новой
перемешки, а не с начала той же. Нескачанный трек в офлайне
не стартует и пропускается
свайпом: сохранённая ссылка потока (`SkyFiStreamUrls`) —
адрес Яндекса, браузер играет её из своего кеша без нашего
бэкенда. Удаление скачанного эту ссылку не трогает.

## 9. Скачивание и предзагрузка

**Скачивание** (единица — трек; альбомы/плейлисты — пакетно):
`POST /audio/file` по снапшоту → файл + рядом сохраняем снапшот
(метаданные). Индекс по паре `(source_type, source_id)` в
локальной БД. Докачка при обрыве (Range/рестарт), удаление,
очередь закачки с приоритетом «вручную добавленное». Менеджер —
в Настройках (список, место, очередь). Видео не качаем.
На вкладках избранного (треки / плейлисты / альбомы / артисты)
над списком строка: слева число элементов, справа «скачать
всё» (кружок со стрелкой, в процессе спиннер с процентом
по трекам пакета, готово — «Скачано»). Загрузки и Скачано —
без этой строки. У альбома и плейлиста на строке то же кольцо,
пока скачаны не все треки: в базу сразу пишется полный порядок
`trackKeys` и `total`. Открытая деталка целиком скачанного
альбома или плейлиста берётся из базы, `POST /details` не
зовётся. Неполный — деталка запрашивается.

**Предзагрузка**: смена трека должна быть мгновенной. Греем **только
ссылки** (байты не трогаем): устройство воспроизведения по живому
держит 2 трека вперёд и 2 назад (волна — та же схема, окно её
контекста движок берёт как обычный список). Скачанный трек в это
окно не входит и `audio/get-url` для него не запрашивается — играет
локальный файл. Окно считает движок
(`peekAdjacent` — прогулка resolveNext/Previous по симулированному
состоянию: очередь приоритетнее, затем контекст с repeat/shuffle).
**Кеш stream URL** (`lib/stream-url-cache.ts`, IndexedDB
`SkyFiStreamUrls`): ответ get-url живёт по ключу
`(source_type, source_id)` до истечения ttl и переживает
перезагрузку — текущий трек плеера не запрашивает get-url
заново, пока ссылка свежая. Свежая — не просим повторно,
дохлая (ttl вышел, с запасом 5 с) — выметается из памяти и
базы, и трек, которому нужна ссылка, запрашивает get-url
снова. В
клип-режиме ближайший трек вперёд дополнительно резолвим
(`/videos/resolve`, не чаще раза в 5 мин на трек) и греем get-url
видео — переход в клип без ожидания матчинга. Только активное
устройство, только онлайн, на паузе молчим; ошибки предзагрузки
глотаются. Буферизация байт (отдельный элемент на следующий трек)
осознанно отложена: видео-буфер дорог (десятки МБ, второй hls.js),
выигрыш после тёплых ссылок мал — решение по замеру реальных stall'ов.

## 10. Сокеты-клиент

Echo + Reverb (api.md §17). Слой — `src/realtime/` (единый фасад:
`startRealtime/stopRealtime`, статус, `bindSessionRealtime()` из
main.ts рядом со startPolling; роутер `router.ts` даёт каждому ивенту
эхо-глушение по origin_device_id и дедуп по command_id). Хендлеры
только пишут в Pinia-сторы; UI о сокетах не знает. Готовность по
этапам — docs/plan-sockets.md.

Правила:
- Подписка на свой канал + `friends.{id}` друзей (друзья — этап 3).
- Устройства (этап 1, готово): `playback.device.*` → `stores/devices`
  (presence-список, «это устройство» по device_uuid); presence —
  регистрация по uuid + heartbeat 30 с (пауза в фоне на нативе).
  `device.changed`/`device.disconnected` дополнительно патчат
  `active_device_id` в стейте плеера (удалённое активное → null).
  `device.connected` с незнакомым uuid (после сида списка) — тост
  «новое устройство в сети»; список сидится GET'ом при регистрации
  и перечитывается при каждом открытии шита устройств.
- На `playback.state.updated`: если `version` новее локального
  — применить; если `origin_device_id` = мой device_uuid — пропустить
  (своё эхо).
- На `playback.queue.updated`: item != null — тост
  «{title} — {artists} добавлено в очередь» + рефетч очереди;
  null — рефетч очереди.
- На `friend.queue.item.added` — тост «{added_by.name}
  добавил: {title}» + рефетч.
- Reconnect — `GET /player`: пульт полностью подменяет зеркало;
  активное устройство — слияние по владению (frontend.md §5).
  Хук `onRealtimeReconnect`.
- Дев-связка https + сокеты: dev-сервер на basicSsl (https) — нужен
  камере сканера QR и clipboard (secure context). Reverb на бэке
  plain ws, а https-страница не может в ws:// (mixed content), поэтому
  dev гонит сокеты через прокси vite: при `VITE_REVERB_PROXY=true`
  клиент стучится в wss://<dev-сервер>/app/{key} и /broadcasting/auth,
  vite пересылает на ws://VITE_REVERB_HOST:PORT (см. server.proxy в
  vite.config.ts). В проде флаг выключен — прямое подключение по
  VITE_REVERB_*. Слой пишет в консоль с префиксом `[realtime]`: адрес
  подключения, статусы, входящие ивенты и причины пропусков.

## 11. Локальное хранилище

- Сессия (токен) — защищённое хранилище (Capacitor Preferences
  Secure Storage).
- Кеш избранного целиком (снапшоты) — локальная БД
  (Dexie/IndexedDB в браузере, SQLite на нативе — по решениям
  шага 2).
- Очередь мутаций, индекс скачанного, кеш stream URL —
  локальная БД.
- История поиска (`skyfi.search-history`), громкость
  (`skyfi.player-prefs`) — Capacitor Preferences, то же
  хранилище, что у сессии. В браузере это localStorage, на
  телефоне — настройки приложения. Режим клипов здесь не
  храним: серверный `clips_enabled` — источник истины.
- Состояние UI — Pinia stores (плеер-стор как единый источник
  для UI и MediaSession).
