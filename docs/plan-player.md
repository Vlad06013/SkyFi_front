## 0. Модель команд (решено 2026-11-23)

Две категории команд плеера:

- **Прямой запуск** — `POST /play` со снапшотом: «включи
  конкретно это». Шлют все устройства при тапе по треку;
  активное устройство шлёт же на автопереходе (`ended` —
  движок уже вычислил снапшот). Тап по элементу очереди —
  тоже прямой запуск + статус `playing_now`.
- **Команды управления** — next/previous: «сделай шаг
  вперёд/назад в своём контексте». НЕ указание трека.
  Исполняет только активное устройство, своим движком, по
  своему контексту/окну волны (у пульта волны нет окна —
  ему и не нужно). Своя кнопка на активном — без сети:
  движок локально → `/play`; пульт — через ретранслятор.

Ретранслятор на бэке (вопрос №7в) — не нужен (решено
2026-11-23, сверка с бэком): у всех источников есть списки,
контекст каждое устройство восстанавливает сам по паре
`play_source` + `context_ref`. Next/prev пульта — вычисленный
`/play` (пульт волны — без next, см. §2).

Транспорт (pause/resume/seek) и настройки (shuffle/
repeat через `PATCH /options` с роллом seed) — существу-
ющие команды, без изменений. Следствие: пультам контекст
нужен только для превью-слайдов, не для переходов.

## 1. Кнопки и переходы

### Движок переходов

Один модуль (`lib/playback-engine.ts` + обвязка в сторе):
чистые функции `resolveNext(reason)` / `resolvePrevious()` по
текущему состоянию. Ими пользуются кнопки, свайпы и автопереход
по `ended`, и превью карусели MiniPlayer (`previewNext/previewPrevious`
считаются тем же кодом, что и реальный переход). Кнопки/свайпы
шлют команду управления (§0) — движок на этом вызывается
только на активном устройстве, пульты получают готовый стейт.

### Next

1. **Ручной next** — всегда очередь/контекст, игнорирует
   `repeat=one` (one повторяет только автопереход).
2. **Автопереход (ended):** `repeat=one` → тот же снапшот,
   `/play` с ним; иначе очередь → контекст; конец контекста +
   `off` → избранное с начала (бесконечная игра, принято в
   frontend.md §5).
3. Очередь приоритетнее контекста. repeat=one перебивает
   очередь **только на автопереходе** (решено 2026-11-23,
   отраслевой дефолт Spotify/Яндекс Музыка: трек крутится,
   пока повтор не выключат или не нажмут next); ручной next
   идёт в очередь как обычно.

### Prev

Позиция < 3 с (порог `skipRestartAfter`, уже в сторе) →
рестарт (`POST /seek {0}`); иначе предыдущий в виртуальном
потоке (очередь включена; возврат после очереди — через
`previous_play_source_snapshot`). Дальше назад некуда
(начало контекста, передний край окна волны, single) →
рестарт **всегда, независимо от repeat** (глобальное
правило плеера, решено 2026-11-23).

### Repeat

- `one` — только автопереход: ended → тот же снапшот;
  **перебивает очередь** (непустая очередь ждёт выключения
  повтора или ручного next — решено 2026-11-23).
- `all` — цикл по контексту (по перемешанной копии при shuffle).
- `off` — конец контекста → переход в избранное с начала
  (новый контекст FAVORITES), плеер не остаётся пустым.

## 2. Контекст

### Что есть контекст

**Контекст = источник (`play_source`) + ссылка (`context_ref`) +
список элементов, материализованный локально.** Курсор не
храним — выводится из `current_snapshot` поиском в списке.

Формирование — в момент старта воспроизведения:

- Тап по треку в списке → контекст = весь список,
  `play_source` по экрану, `context_ref` — что есть (id
  плейлиста, query поиска, null).
- `single` — вырожденный контекст из одного трека; next →
  избранное с начала.
- `wave` — окно живёт на бэке (api.md §14, решено
  2026-11-23): сервер держит курсор по `current_snapshot`
  плеера, сам догружает порции и чистит прослушанное;
  волна единая на аккаунт. Клиент синхронизирует окно
  целиком: `GET /wave` → полная замена локальной копии;
  `playback.wave.updated` → рефетч + полная замена, без
  диффинга. Движку волна = обычный контекст (элементы =
  окно); шаг внутри волны — обычный `POST /play` со
  снапшотом из окна (`playback_source=wave`), бэк сам
  перестраивает окно вокруг него. Prev-история локальная.
  Shuffle на волне отключён. Feedback Яндексу — позже.
  Пульт волны: текущий трек + play/pause/seek, без превью;
  next на пульте в MVP неактивен (remote-next на волне
  потенциально возможен позже: окно общее, пульт знает
  следующий снапшот — отдельное обсуждение).
- Пагинация: контекст лениво расширяется (next за пределами
  загруженного → догружаем страницу), не материализуется целиком
  при старте.

### Синхронизация контекста между устройствами

Синхронизируем **указатель, не содержимое**: в state —
`play_source` + опциональный `context_ref` (playlist → его
source_id, search → query, favorites/uploads/single → null,
волна живёт в `wave_anchor`) + `shuffle_seed` (см. ниже).
Каждое устройство по паре само фетчит список обычными API —
они идемпотентны.

Почему не items в state: снапшоты тяжёлые, волна — бесконечный
список, state раздуется и поедет по сокетам на каждый чих.
Почему не курсор-индекс: список живой (лайк/сортировка с другого
устройства сдвинет индексы), `current_snapshot` — стабильный якорь.

Дыра контракта: playlist/search на пульте сейчас не восстановить
вообще (`play_source=playlist`, какой плейлист — неизвестно).
Вопрос №1 к бэку.

### Shuffle — детерминированная перестановка (уточнено 2026-11-23)

- Порядок = **hash-сортировка** элементов контекста по ключу
  `hash(shuffle_seed, source_type + source_id)` (не FY по
  массиву: элементы при ленивой пагинации встают в середину,
  не перетасовывая известные). Один seed + один список =
  одинаковый порядок на всех устройствах, всегда.
- **`shuffle_seed` хранится в стейте плеера** (вопрос №6 к
  бэку): инициатор play/включения shuffle генерирует случайный
  ключ и кладёт в команду; остальные устройства только читают.
  Бэк ключ не интерпретирует — хранит и отдаёт как есть.
- Ролл ключа — ровно два случая: пользовательский `/play`
  (тап по треку/кнопка play списка) и включение shuffle
  (выкл→вкл = «перемешать заново», текущий трек не рвётся).
  Выключение shuffle шлёт null. Движок (next/prev/auto,
  repeat-one, очередь, возвраты) ключ не трогает; перезапуск
  приложения и reconnect — тоже.
- Fallback без поля в контракте: статический seed
  `hash(user_id, play_source, context_ref)` — порядок «вечный»,
  но консистентный между устройствами.
- Курсор = позиция `current_snapshot` в перестановке; prev =
  сосед слева → серверная история не нужна, prev живёт после
  перезапуска.
- **Очередь не перемешивается** — порядок её фиксирован
  сервером и ручной сортировкой («очередь = друг за другом»);
  shuffle перемешивает только сегмент контекста виртуального
  потока.

### Что где хранится

| Что | Где | Почему |
|---|---|---|
| `play_source`, `context_ref`, `shuffle_seed` | сервер (`PlayerStateView`) | без ref/seed устройства не восстановят контекст и перемешанный порядок |
| `current_snapshot` | сервер | уже есть, служит курсором |
| items списка | только локально (Pinia + кеш), фетч по ref | содержимое восстанавливаемо, по сокетам не гоняем |
| курсор-индекс | нигде | выводится из `current_snapshot` |
| история (для prev) | локально, из потока состояний | после перезапуска prev = предыдущий в перестановке/списке |
| очередь | сервер (api.md §6) | уже реализовано |

Fallback: `current_snapshot` не найден в списке (убрали из
избранного на другом устройстве, протухла выдача поиска) →
next = начало списка/перестановки. Редкий кейс.

## 3. Позиция

Механика периодического репорта остаётся, с двумя поправками:

- **Репорт по событиям**, не только таймером: pause, seek,
  смена трека, сворачивание/закрытие приложения, смена активного
  устройства — сразу. Таймер (10 с) — страховка от краша.
- **Quiet-флаг**: position-only репорт не должен диспатчить
  `playback.state.updated` всем пультам (иначе каждые 10 с все
  устройства перерисовывают плеер ради секунд прогресса).
- Идеальный вариант — серверное время в state
  (`position_updated_at`): пульт экстраполирует позицию сам
  (`position + now - updated_at` при `is_playing`), таймер можно
  раздуть до 60 с или убрать.

Если бэк ничего не меняет — 10 с работает, легаси-поведение,
не блокер.

## 4. Офлайн и скачанное

**Офлайн меняет не контекст, а resolver контекста.** Контекст
остаётся логическим (source + ref), список материализуется из
локальной БД скачанного/кеша вместо API.

- Избранное офлайн = тот же контекст `favorites`, фильтр
  «только скачанные» (принято в frontend.md §8).
- Уход в офлайн посреди трека: трек скачан → играем дальше без
  шва, позиция целая. Не скачан → авто-переход к ближайшему
  скачанному впереди по контексту; нет ни одного → пауза + тост.
- Очередь офлайн: элементы без локального файла пропускаются
  (в UI — disabled), порядок сохраняется.
- Локальная волна офлайн — отдельный контекст-режим (радио по
  скачанному + кеш), frontend.md §6.
- Возврат онлайн: resolver переключается обратно на API,
  контекст не пересоздаётся — `current_snapshot` и курсор легли
  на те же места.

В коде: `resolveContext(source, ref)` →
`online ? fetchFromApi() : queryLocalDb()`; логика переходов
разницы не знает.

## 5. Кросс-девайс и применение состояния

- Звук воспроизводит только устройство, чей серверный id ==
  `state.active_device_id`. Остальные — пульт: UI синхронизируется,
  аудио молчит.
- Роли (решено 2026-11-23): **активное устройство — истина
  воспроизведения**, серверу репортит; **пульты — зеркала
  серверного стейта** (приоритет: ответ команды → сокет-ивент
  с version-gate → `GET /player` на reconnect, полная подмена
  зеркала). Эхо-глушение и dedup по `command_id` — уже в
  `realtime/router.ts`.
- Активное устройство применяет из сервера ровно три вещи:
  чужую команду (`origin_device_id` ≠ мой) — выполняет как
  команду движку; смену `active_device_id` — глушит аудио,
  становится пультом; reconnect — слияние по владению
  (frontend.md §5): поля координации (`active_device_id`,
  очередь, `play_source`/`context_ref`, `shuffle_seed`,
  presence, version) из сервера, воспроизведение — своё,
  если активное устройство всё ещё мы.
- Оптимистичность: play/pause — с откатом по ошибке; остальные
  команды — по ответу сервера, с индикацией полёта; при сетевой
  ошибке — тост + `GET /player` resync. Повторные next —
  дебаунс/блокировка, чтобы не спамить `/play`.
- Локальная копия: последний стейт + контекст пишутся в Dexie
  на каждом переходе (глобальная запись `player_state`) —
  мгновенный старт UI и офлайн-рестарт без сети.
- Переход на элемент очереди: `POST /play` + `PATCH status
  playing_now`, при покидании — `played`/`skipped`. Два запроса
  без транзакции — гонки возможны (см. вопрос 4 к бэку).
